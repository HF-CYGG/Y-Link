# Y-Link v1.6.0 与 v2.0.0 版本排期

> 文档说明：本文是 v1.6.0、1.6 系列后续迭代与 v2.0.0 的版本范围与排期规划，依据 2026-09-28 对 `main@60539d8`（应用版本 `v1.5.51.21`）的架构评估制定。
> 维护口径：本文属于规划文档，描述的是目标态而非已上线事实。每完成一项，请把对应复选框改为 `[x]` 并注明提交号；范围或日期调整时直接修改本文，并在文末“变更记录”追加一行。
> 执行约束：所有任务仍须遵守仓库根 `AGENTS.md`（中文、先读上下文文档、验证命令、风险说明）。引入任何新依赖前，必须先单独说明原因、收益与风险，经负责人确认后再落地。

## 1. 版本划分原则

判断标准：升级后，**部署者或接口调用方是否必须改动才能继续使用**。

| 类型 | 判断依据 | 归属 |
| --- | --- | --- |
| 纯工程治理 | 应用行为不变（lint、CI、测试框架、依赖扫描、仓库清理） | 随 v1.6.0 一起发布，不单独递增版本 |
| 兼容的质量改进 | 行为可见但完全兼容，用户无需任何操作 | v1.6.0 与 1.6 系列 |
| 破坏性变更 | 部署方式、数据库结构、必需依赖、接口路径或错误格式至少一项改变 | v2.0.0 |

版本号约定：

- 1.6 系列继续沿用现行四段式规则（见 `docs/版本发布历史与更新日志.md`）：v1.6.0 对应展示版本 `v1.6.0.0`；此后的功能批次按规则递增第三段，因此本文中的“迭代 A/B/C”只标注范围，不预先指定版本号。
- 从 v1.6.0 起，每次发布都打 git tag（如 `v1.6.0`），镜像同步发布同名版本标签；README 引导用户锁定版本号，而不是拉取 `latest`。
- v2.0.0 起改为三段式 SemVer（主.次.修订），应用展示版本、npm 包版本、git tag 与镜像标签统一。

## 6. 升级路径

```text
v1.5.x ──直接替换镜像──> v1.6.0 ──> 1.6 迭代 A/B/C ──> 1.6 桥接版本
                                                          │
                                   运行升级预检 + 完成 SQLite→MySQL 迁移
                                                          │
                                                          ▼
                                                       v2.0.0
```

- 1.5 → 1.6.x：完全兼容，替换镜像即可。
- 1.6 桥接版本 → 2.0.0：必须先通过升级预检；仍在使用 SQLite 的部署需先用桥接版本内的迁移向导迁到 MySQL。
- 不支持从 1.5 或早期 1.6 版本直接跳到 2.0.0。

## 7. 主要风险与应对

| 风险 | 影响 | 应对 |
| --- | --- | --- |
| 金额统一改变历史订单的舍入结果 | 对账差异 | W3 用存量订单比对，差异在更新日志中公示 |
| onebox 改为非 root 后，旧数据目录无写权限 | 升级后无法启动 | 启动脚本自动修正属主，并用旧目录做升级演练 |
| 2.0 取消 SQLite 生产部署，对 1Panel 新手门槛上升 | 部署复杂度增加 | 提供双容器 compose 与 1Panel 图文指引；桥接版本内置迁移向导 |
| 存量 MySQL 库与基线迁移不一致（历史上手工执行过部分 SQL 脚本） | 升级 2.0 时启动失败 | 基线对齐前先做结构校验；桥接版本的升级预检提前发现差异并给出修复脚本 |
| 春节前后人力不足 | M3、M4 延期 | 预留 2 周缓冲；M4 可拆出“数据权限”顺延到 2.1 |
| 单人开发，范围过大 | 整体延期 | 以 1.6 桥接版本为最低交付；2.0 中无状态化与领域模型可按优先级顺延到 2.1 |
| 新依赖带来的供应链与维护成本 | 安全与升级负担 | 每个新依赖单独评审，并纳入 Renovate 与 CodeQL 监控 |
