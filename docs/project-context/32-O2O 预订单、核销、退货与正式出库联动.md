# Y-Link O2O 预订单、核销、退货与正式出库联动

## 适用范围

- 适用于 O2O 下单、改单、核销、退货、超时回收、库存日志和正式出库单联动场景。
- 适用于定位“为什么库存先占用、为什么核销后生成出库单、为什么退货有时回预占有时回现货”的问题。

## 真实入口

- 客户端下单入口：`POST /api/o2o/mall/preorders`
- 客户端改单/撤销/退货入口：`/api/o2o/mall/preorders/*`
- 管理端查询/核销/现场改单入口：`/api/o2o/orders*`、`/api/o2o/verify*`
- 管理端出库单合并入口：`POST /api/orders/merges/preview`、`POST /api/orders/merges`
- 服务真源：`o2o-preorder.service.ts`

## 前端链路

- 客户端订单列表和详情页主要围绕 `pending / verified / cancelled` 展示，并附带状态报告对象。
- 客户端订单列表/详情同时展示当前父单号与本人原始正式出库单号：当前单号用于后续查询和打印，原始单号用于说明合并前身份；详情和退货入口仍绑定当前登录客户自己的预订单。
- 管理端有三类入口：订单查询、核销控制台、入库/库存日志协同页。
- O2O 前端既要显示预订单本身，也要展示是否已产生正式出库单、是否存在退货申请、是否有商家留言和业务状态。

## 后端链路

- `o2o-preorder.service.ts` 是完整闭环真源，负责：
  - 商城商品列表和门店配置
  - 预订单创建、查询、详情、摘要
  - 客户端改单、撤销和退货申请
  - 管理端订单查询、业务状态、商家留言、现场改单
  - 预订单核销、退货核销
  - 超时自动取消与库存释放
  - 正式出库单创建
  - 库存日志写入
- `o2o.routes.ts` 明确分成：
  - 客户端匿名商品接口
  - 客户端鉴权后的订单接口
  - 管理端查询/核销/库存接口

## 关键状态/字段/快照

- 核心库存口径：
  - `currentStock`：现货库存
  - `preOrderedStock`：预订单占用库存
- 预订单核心状态：`pending`、`verified`、`cancelled`，并叠加 `businessStatus`、`statusReport`。
- 价格快照采用 `originalPrice`、`discountRate`、`discountedPrice`、`unitPrice`、`lineAmount`，避免实时产品价格污染历史订单。
- 规格快照采用 `skuCodeSnapshot`、`specTextSnapshot`、`skuImageSnapshot`，退货明细同样继承下单时的规格快照。
- 明细行的规格展示口径统一收口在 `src/utils/o2o-item-spec.ts`，由 `BizO2oItemSpecText` 组件渲染：
  - 真实规格正常展示；`默认规格` 属单规格商品，不再渲染标签；
  - 规格文本缺失但仍有 SKU 编码时展示编码兜底；SKU 化改造前的历史订单显式提示“未记录规格”；
  - 任何情况下都不得回查当前商品 SKU 补全，避免商品改名、改规格或下架后污染历史订单展示。
- 出库单商品名快照由后端 `createOutboundOrderFromPreorder()` 拼成 `商品名（规格）`，客户端出库单预览用 `buildO2oItemDisplayName()` 保持同口径。
- 预订单核销成功后会生成正式出库单，并用特定 `idempotencyKey` 前缀与出库单建立联动。
- 退货核销是否回现货库存，取决于原订单在退货时的来源状态。
- 正式出库单通过 `o2o-preorder-verify:<preorderId>` 关联原预订单。合并后目标原订单是父根、来源原订单是一层子单，不生成新单号；父单沿用自身号，来源客户查询时返回当前父单号并保留本人原始号。服务端按 `clientUserId` 裁剪详情、摘要、退货和打印接口，跨账号访问返回 404，不泄露他人原始号或明细。
- 退货申请的 `orderId` 始终绑定本人原预订单，不改绑到父单；来源单存在待处理退货时禁止合并，合并组任一预订单存在待处理退货时父单软删除也被原子阻断。父单软删除/恢复同步父及全部来源预订单的可见性。
- 客户打印锁定整个 O2O 合并组的出库单证据；来源客户打印会同步父单，之后目标父单不得追加合并，管理端保存不能清除合并成员已经置位的打印证据。管理端调整 `isSystemApplied` 时只更新对应原预订单及来源正式单，父正式单按全组状态 OR 聚合，其他账号的原预订单保持不变。合并成员的永久删除由服务端关系门禁阻断。

## 权限与安全边界

- 客户端所有订单动作都必须经过 `requireClientAuth`。
- 管理端查询通常依赖 `orders:view`，核销与正式出库联动依赖 `orders:create` 或 `orders:update`。
- 删除订单池单据还需要 `orders:delete`、管理员角色和永久删除密码。
- 客户端与管理端不允许各自维护不同的价格/库存真相，必须以服务层快照为准。
- O2O 核销生成的正式出库单显式标记为 `o2o_preapplied`：其库存已由预订单核销链路完成扣减，通用订单内容编辑入口必须锁定，避免二次扣库或破坏预订单快照。
- O2O 合并沿用 `orders:merge` 权限和订单合并 preview/commit 协议；同部门、同一服务器本地统计日的不同客户可合并，但跨账号读取仍受客户端归属校验保护，跨统计日正式出库单不得首次合并或继续追加。

## 常见异常与排查顺序

1. 下单后库存没占用：查服务层是否写了 `preOrderedStock` 和库存日志。
2. 核销后没生成正式出库单：查 `verifyPreorderInManager()` 和出库单创建逻辑。
3. 退货后库存回错位置：查退货来源订单状态和 `applyReturnVerificationForItem()`。
4. 订单状态展示奇怪：查 `statusReport` 与 `businessStatus` 是否同时生效。
5. 同一订单删了出库单后显示异常：查正式出库单与预订单可见性联动。
6. 合并后当前号/原始号不一致：查 `resolveCustomerOrderShowNoMap`、父子关系和客户端 `resolveO2oDisplayShowNo`，不要回查实时商品或改写预订单归属。

## 验证与回归关注点

- 客户端回归：下单、改单、撤销、退货申请、订单详情。
- 管理端回归：订单查询、业务状态、商家留言、现场改单、核销、退货核销。
- 联动回归：库存日志、正式出库单生成、超时回收、删除治理后的可见性。
- 合并专项：`npm --prefix backend run order:merge:verify`（其中 O2O 子场景覆盖同部门跨客户、同本地统计日与跨日门禁、当前/原始单号、跨账号 404、打印锁、退货绑定、pending return 阻断、父删恢复和永久删除门禁）。
- 迁移/结构与并发：`npm --prefix backend run order:merge:migration-fixture:verify`、`npm --prefix backend run verify:mysql:schema-contract`、`npm --prefix backend run verify:db:concurrency`。
