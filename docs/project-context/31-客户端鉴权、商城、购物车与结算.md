# Y-Link 客户端鉴权、商城、购物车与结算

## 适用范围

- 适用于客户端登录、注册、找回密码、商城浏览、购物车、结算和个人中心场景。
- 适用于定位“刷新后为什么还能登录、购物车为什么会保留、换号为什么要清缓存”的问题。

## 前端链路

- `client-auth.ts` 启动时先读本地快照，再调用 `/client-auth/me` 校验服务端 Cookie 会话是否仍有效。
- 客户端新密码（注册、找回重置、个人中心改密、管理员代设）为 8-64 位且同时含字母和数字，后端另拦截常见弱口令、重复字符过多、包含系统名称或本账号手机号/邮箱/用户名/工号的口令，前端展示后端返回的原因（口径见 `42-权限、Cookie、CSRF、审计与上传安全.md`）。
- 登录、注册、找回密码、资料更新统一通过客户端鉴权 Store 收口；教师注册仍提交 `inviteCode` 字段，但其含义是管理员统一配置的 8 位数字邀请码。
- 购物车 Store 在本地持久化的不只是商品和数量，还包括价格、库存、限购和选中态。
- 商城和购物车展示共用 O2O 价格口径工具，避免页面各自计算折扣价。
- 结算页提交成功后通常跳订单详情，因此客户端路由预热把订单详情放在高优先级。
- 部门账号每次进入结算页都须填写实际领取人姓名（教师姓名），不读取旧草稿，也不从账号实名回填；散客继续沿用提货人默认值与草稿。领取人与到店取货时间共同构成提交意图。结果未知时独立展示原提交摘要，继续确认只使用首次请求键与完整原载荷；此恢复流程不会给一笔新的部门单回填姓名。

## 后端链路

- `client-auth.middleware.ts` 优先从客户端安全 Cookie 读取会话，再兼容 Bearer。
- 客户端会话失效时，服务端直接返回未登录，由前端 Store 清理本地快照。
- 管理员注销客户端账号时会在同一事务强制 `status=disabled`、删除 Web 会话并撤销 Mobile access/refresh 会话，提交后断开该账号 SSE；恢复仅解除注销态，账号仍保持停用，必须另行显式启用。
- 商城商品来自 O2O 商品接口，而不是单独的客户端商品表。
- 商城目录 `/o2o/mall/products` 与门店展示 `/o2o/mall/storefront`（商品详情直接取自目录快照，没有独立接口）在进程内快照之后还有 Redis 二级缓存：键名带 Redis 中的集群修订号，任一实例目录写入提交后先 `INCR` 修订号再广播，提交后的读取不会命中旧快照；共享快照有效期与进程内新鲜期一致（目录 2 秒、门店 5 秒），各实例返回同一响应体，ETag 一致。结算与下单始终回源数据库校验库存。
- 新商品上架的客户端可见时延：后端写入提交即失效全部实例的目录缓存；Nginx 对浏览器返回 `Cache-Control: public, no-cache`，浏览器每次按 ETag 条件请求（未变化时 304），回源压力由 Nginx 5 秒共享微缓存吸收；`ClientMallView.vue` 在本地快照有效期内先秒开再后台重新校验，停留在商城页时每 30 秒、切回前台时也静默校验。正常情况下新商品在数秒到约 35 秒内出现在已打开的商城页，无需顾客手动刷新。
- 新个人注册及主动改名仅接受 2–20 位中文或英文字母，禁止数字、空格和特殊字符；资料页复用注册规则并直接提交校验后的原始姓名，历史姓名未修改及教师目录姓名不强制套用新规则。
- 重名仍拒绝，不开放同名账号注册；注册须先完成联系方式验证码核验，重名与联系方式重复统一返回不可用提示，前端统一引导联系管理员，不披露具体冲突账号。
- 教师目录姓名与历史账号登录保留兼容，历史姓名未修改时仍可保存资料，不执行批量改名。
- 教师身份以非空 `staffNo` 为真值，不依赖 `staffVerified`；注销期间不得编辑或释放工号、姓名、联系方式等唯一身份，避免同一身份被重复注册。

## 关键状态/字段/快照

- 客户端鉴权快照核心字段：`currentUser`、`expiresAt`、`initialized`。
- 购物车可购量统一用 `resolveClientCartMaxQty()`，即 `availableStock` 与 `limitPerUser` 的合并口径。
- 数量支持直接输入（Issue #97）：迷你购物车、购物车抽屉和商品详情弹层共用 `components/ClientQtyInput.vue`，输入中只保留本地草稿，失焦或回车才提交；购物车走 `setQtyFromInput()` 再交给 `updateQty()` 按可购量收口，详情弹层走 `commitDetailQty()` 按 `detailMaxQty` 收口。空值、非数字或小于 1 的输入只提示不写入，不得写入 NaN 或把输入 0 当成删除；移除商品仍走减号或删除操作。
- 目录刷新及缓存恢复必须保留原选数量和勾选状态；`syncWithCatalog()` 仅刷新库存、价格及可购状态，缺失商品/SKU 标记不可购。
- 购物车本地缓存是可失败的恢复辅助项：访问、读写或清理异常不能阻断内存更新和目录同步；读取失败按空购物车恢复，写入失败时本次修改可能无法在刷新页面后恢复，但不放宽网络刷新、库存校验与账号隔离。
- `selectedCheckoutConflicts` 汇总全部已选行的库存/规格冲突，不能过滤无效选中项后提交剩余商品；用户主动调整、取消选择或移除后才可下单。
- 新提交先成功刷新目录再校验并固定一次性请求快照，失败不提交。首次 POST 前必须成功写入并读回 version=2、owner、原 requestKey、完整原 payload 与 30 分钟原始到期时间的 `sessionStorage` 记录；存储读取、写入或读回异常时不得发送。
- 无响应、408 和全部服务端 5xx 属于结果未知，刷新后显示原提交摘要，可继续确认原提交或查看订单。确认原提交直接使用持久化的原载荷（包含备注内部空白、提货人、取货时间和金蝶编号），不得从有损 `intentKey` 重建，也不得采用当前购物车替代；重试不延长原期限。
- 当前结算页面仍有效时，成功响应先同步已确认的购物车商品再清理原提交记录；若成功回包时页面已失效，保留原 key 与恢复记录，不更新新账号界面，避免保留购物车却生成新 key。确定拒绝可清理原提交记录。旧版、损坏、归属错误或已到期的记录仅提供查单提示，不自动重发、不宣称失败、不静默生成新请求键。退出/换号同步清除页面业务输入，并将原记录转换成无业务明文的 pending 标记，连同含业务 JSON 的 `intentKey` 一起清除，保留原期限。
- 商城已打开的详情在目录替换后按 product/SKU ID 关联新对象，保留有效规格选择与原数量；价格、库存或限购变化展示提示，超出新上限需用户主动调整。下架商品和失效 SKU 不自动切换到其他规格，不能把旧快照加入购物车；失效后只剩一个有效 SKU 时仍显示明确的选择按钮，用户点击后才关联该新对象。
- 商城搜索索引仅随目录内容更新生成，包含当前启用 SKU 的 `skuCode`、`specText` 和 `specValues` 值；禁用/历史 SKU 不参与匹配，排序和分页沿用原逻辑。

## 权限与安全边界

- 客户端登录态不应由本地缓存单独判定，必须以后端 `/client-auth/me` 校验结果为准。
- 退出登录和账号切换时必须清理购物车、目录、订单等用户绑定缓存，防止串号。
- 客户端页面不应绕过 Store 直接判断 Cookie 是否存在。
- 教师注册邀请码由后端按当前统一配置校验，前端只做 8 位数字格式提示，不缓存、不展示或推断邀请码状态；单工号失败锁定和同工号唯一注册继续由服务端事务保证。
- 手机号与邮箱一经注册即占用，无论是否已验证（含教师注册、管理员建档写入的未验证联系方式）都不允许其他账号再注册或改绑，冲突统一返回不可用提示；不提供验证码接管。
- 教师注册的手机号/邮箱选填，但一旦填写必须与个人注册一样先用图形验证码发码、再提交该联系方式的验证码，注册成功即记为已认证；对应通道未启用时须留空。防止持有统一邀请码者把他人联系方式写进自己账号占用。
- 登录失败锁定按账号主体（`uid:<用户ID>`）计数，手机号、邮箱、姓名、工号共用额度；改密与改资料的旧密码复核失败同样计入，锁定期间正确密码也被拒绝。
- 单个客户端账号最多保留 20 个 Web 会话，新登录超出时淘汰最久未活跃的会话并断开其 SSE。
- 客户端业务写入按账号限频：反馈新建 5 次/10 分钟、追加消息 30 次/10 分钟、提交预订单与撤单各 20 次/10 分钟、退货申请 10 次/10 分钟。

## 常见异常与排查顺序

1. 刷新后自动掉线：查 `/client-auth/me` 是否失败，再查本地快照是否被清空。
2. 换账号后购物车串号：查 `clearClientScopedStores()` 是否执行。
3. 购物车数量异常：查 `resolveClientCartMaxQty()`、`selectedCheckoutConflicts` 和商品目录最新库存，禁止后台静默缩量。
4. 商城价格和购物车价格不一致：查是否统一使用 O2O 价格工具。
5. 结算后没跳正确页面：查路由预热和结算成功后的跳转逻辑。
6. 教师注册提示邀请码无效：先核对工号目录状态、管理员是否启用统一邀请码，再查服务端的单工号失败锁定与唯一注册校验。

## 验证与回归关注点

- 客户端鉴权回归：登录、刷新恢复、退出登录、找回密码、教师注册的统一 8 位邀请码格式提示与原有 `inviteCode` 请求字段。
- 商城链路回归：加购、改数量、清空、切换账号、刷新后恢复；卡片步进器展开与收拢、详情在有货和缺货规格间切换时底栏的合并与拆分、清空后再次加购刷新仍可恢复。
- 结算链路回归：下单前校验、提交成功跳转、库存不足提示。
- 商城悬浮层回归：商城页挂在布局的绝对定位舞台里，布局层底部留白到不了内容尾部。搜索结果、空结果、分类、推荐和大数据量虚拟列表滚到底时，末项必须完整位于悬浮购物车上方。页面尾部留白、分类浏览列表高度（与分类栏等高）和 `scroll-padding-bottom` 统一由摘要栏实测遮挡高度 `--mall-floating-occlusion` 驱动（计算函数在 `client-mall-viewport.helpers.ts`）。页面滚到底时列表底边恰好停在购物车上方，列表尾部只保留渐隐遮罩所需的 2rem，卡片悬停放大不得撑出横向滚动条；列表的 `100dvh` 约束前必须保留 `100vh` 回退。
- 商品原图预览回归：`components/ClientImagePreviewer.vue` 打开时完整适配原图，只在右上角保留一个关闭按钮。鼠标滚轮以指针为锚点缩放（被动监听，舞台不可原生滚动且页面滚动已锁定，符合 `verify:passive-wheel`），按住左键或触屏按住拖动平移，双击在适配与 2 倍之间切换；键盘保留 Esc / + / - / 0 / 方向键。遮罩不使用 `inset` 简写。问题设备需要人工回归。
- 专项命令：`npm run verify:client-mall-floating-layout`、`npm run verify:client-cart-reconciliation`、`npm run verify:client-registration-policy`、`npm --prefix backend run o2o:stock-consistency:verify`、`npm --prefix backend run client-auth:registration-policy:verify`。


## 商品补货入口

- 商城搜索、虚拟列表、推荐、分类卡片及商品详情接入 `ClientRestockButton`。当前上架启用商品的当前启用 SKU 均可申请，不以库存数量限制资格；期望数量按正整数 INT 范围原样登记，不受现货或购物限购限制，不要求大于现货。
- 卡片仅在当前启用 SKU 恰有一个时提供补货入口；多规格保留选择入口，不在卡片显示补货。卡片名称从图片右侧延伸至卡片右内边距并按单行截断，价格、库存信息与独立操作位于下方；虚拟行高保留原有设置，须在布局验收时核对实际行距。详情选中真实当前启用 SKU 且 `availableStock=0` 时仅显示补货主动作，隐藏数量和加购；切回有货 SKU 恢复数量和加购，正库存仍可通过独立补货表单及单规格卡片申请；加购仍受既有库存与限购校验。
- 单规格先通过活跃申请接口查询，已有有效申请直接打开原会话；新申请进入 `/client/feedback/create?type=restock&productId=...&skuId=...`，不改动购物车或库存。
- 卡片补货按钮（`ClientRestockButton`，文案“申请补货”）与详情底栏共用 `src/composables/useClientRestockEntry.ts` 的查询与跳转逻辑，返回结果时校验账号未切换。

## 加购交互与详情底栏（PR191 交互细节）

- **卡片步进器**：四套卡片的加购入口统一为 `components/ClientCardCartStepper.vue`。单规格商品点“+ 加购”后，胶囊收缩为“+”圆按钮、“−”圆按钮从同一位置向左滑出、数量淡入；减到 0 由购物车 store 移除该行并反向收拢。多规格商品显示“选规格”（打开详情），右上角角标为该商品各规格已加购总数。当前没有可购库存且购物车里也没有该商品时不渲染步进器，由同列补货按钮成为唯一操作。
- 步进器只读取购物车 store 的 `qtyByItemId` / `qtyByProductId`，加购和减购通过事件交给商城页 `quickAdd` / `decreaseCardQty`，复用 store 既有库存与限购校验及提示；触顶时“+”仅 `aria-disabled` 弱化，仍可点击收到限购或库存提示。操作列固定最小宽度（桌面 5.1rem、手机 4.9rem），展开或收起不改变卡片中间列宽度，虚拟行高 `itemHeight: 98` 不变。
- **详情底栏状态机** `detailActionMode`：`purchase`（当前规格可预订库存大于 0）显示“数量 + 加入购物车”；`restock`（当前启用规格 `availableStock=0`，口径同补货按钮）时数量栏用 grid 行高折叠并设为 `inert`，主按钮换为品牌色，文字先隐去再显现“申请补货”；其余情况为禁用的“暂不可购”。三种状态共用同一个主按钮元素，以实现合并与拆分过渡。无货时详情数量保持 1，不会被收敛为 0。
- **加购反馈**：成功新增后从同商品或规格的可见图片几何中心捕获 `img.currentSrc`，约 520ms 抛物线缩小飞入迷你购物车，再触发角标与栏反馈；详情与批量提交在抽屉隐藏前捕获图源和矩形。最多 6 张在途，不额外请求图片；路由离开、失活和换号清理，减少动效时跳过。购物车立即更新，不等待动画。
- **清空购物车**：迷你购物车“清空”二次确认后调用 store 的 `clearItems()`，只清商品行并持久化。`clearAll()` 仅用于登出和换号，它会解除账号绑定；误用会导致之后的加购不再落盘。
- **商品描述**：管理端为纯文本输入框，历史数据里可能混有 `<p>` 等标签。展示与搜索索引统一经 `src/utils/plain-text.ts` 的 `htmlToPlainText()` 转为纯文本，段落转为换行，`.client-detail-desc` 使用 `white-space: pre-line`。描述始终以文本插值渲染，不使用 `v-html`。
- 不限购（`limitPerUser=0`）时详情不再显示“限购 0”；客户端根容器设置 `touch-action: manipulation`，并去除系统点按高亮，按钮统一使用自身 `:active` 反馈。商品卡悬停上浮只在 `(hover: hover) and (pointer: fine)` 下生效，避免触屏点按后卡片停在抬起状态。
- **商品图**：卡片与详情多规格头部小图优先使用 `thumbnailSmall`（服务端 WebP 缩略图），加载失败时依次回退原图和统一占位图；“查看大图”和单规格大图仍使用原图。缩略图约定见 `22-产品、SKU、标签与 O2O 商品管理.md`。
- 订单详情二维码在 `qrcode` 懒加载完成前显示“二维码生成中…”占位，不再闪现“二维码已停用”；取货时段读取门店配置的 `businessHoursText`，与结算页一致。

## 客户端交互收尾契约
