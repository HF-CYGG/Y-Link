# Y-Link 工作台、报表与出库链路

## 适用范围

- 适用于 Dashboard、排行榜、报表中心、出库开单、出库列表、订单删除/恢复/永久删除治理。
- 适用于查“为什么这个统计口径是这样、为什么单号回拨、为什么 O2O 关联订单一删会联动”的问题。

## 前端链路

- Dashboard 页面显示四宫格、结构占比饼图、出库趋势、Top 产品、Top 客户、最近动态，并支持钻取抽屉。
- 首页“结构占比”区块内的统计区间筛选栏是唯一区间入口，同时驱动三个饼图、趋势图与两个榜单；
  四宫格（今日/本月）与最近动态（审计事件流）不随区间变化。
- 区间筛选状态收敛在 `src/views/dashboard/composables/useDashboardAnalytics.ts`，页面与卡片组件都不自行发起区间查询。
- 出库开单页只允许选择已建档、当前启用且至少有一个当前启用 SKU 的商品，再通过数量/人工单价编辑、汇总卡片和提交动作构造 `SubmitOrderPayload`；单 SKU 自动选中，多 SKU 必须显式选择，SKU `defaultPrice` 只作预填。旧版草稿中的商品名仅在与当前候选唯一且完全同名时迁移为真实 ID，并重新对齐 SKU/价格；未知、重名或失效值会在任何写请求前被拒绝。候选加载失败时不得迁移或持久化恢复草稿，避免清空原 SKU 和人工价。开单流程不再隐式创建零库存商品。
- 部门单的“客户部门”是可搜索、可选择、可手动录入的组合输入：
  - 选项来自 `GET /api/orders/department-options`（依赖 `orders:create`，不依赖系统配置查看权限），
    只读展开系统部门配置 `client.department.options`，按完整路径展示与搜索；
  - 前端只在完整路径唯一命中选项时携带 `customerDepartmentNodeId`，服务端用
    `systemConfigService.resolveClientDepartmentNode` 只读解析出规范完整路径覆盖提交文本，节点已删除时返回 400；
  - 手动录入不携带节点，原样保存为 `customer_department_name` 快照，**不会**创建或修改系统部门配置；
  - 订单只保存完整路径快照，不保存节点 ID；列表、详情、打印、报表、Dashboard 继续按名称使用。
  - 选项加载失败或配置为空时只提示，不阻断手动录入；草稿不依赖节点，恢复后按当前选项重新推导。
- 出库列表页负责筛选、详情抽屉、手工单内容编辑、修订时间线、删除、恢复、永久删除以及合规标记编辑。
- 出库列表页的合并入口由 `orders:merge` 控制：桌面端使用 Element Plus 树表展示父单/来源子单，移动端卡片支持展开来源单；合并弹窗先预览再提交，提交后刷新并支持父子单跳转。已有父单只能继续作为目标父单，来源子单只读。
- 报表中心按报表类型切换字段定义和导出行为，不同报表共用一个前端 API 模块。

## 后端链路

- `dashboard.service.ts` 负责：
  - 今日/本月统计（`getStats`，固定口径，不接受区间入参）
  - 区间分析（`getAnalytics`：趋势分桶 + Top 产品 + Top 客户）
  - 结构占比饼图（`getDashboardPieData`）
  - 最近动态
  - 产品/客户/标签钻取
- `order.service.ts` 负责：
  - 幂等提交
  - 主单/明细事务写入
  - 手工明细 SKU 归属/当前启用状态校验和代码、规格快照
  - 单号生成
  - 产品默认价快照回写
  - 软删除/恢复/永久删除
  - O2O 关联单据可见性联动
  - 流水号安全回拨
- `order-merge.service.ts` 负责订单合并预览与提交：按账号、订单、明细稳定顺序加锁，在事务内校验版本、状态、类型、库存模式、客户/部门、服务器本地统计日和 O2O 约束；目标原订单保留为父根，来源原单成为一层子单，不新建单号、不重复扣库存。
- 合并接口采用 preview/commit 两步协议，`orders:merge` 权限由路由统一门禁；提交使用幂等键和请求哈希，重放返回持久化稳定快照，冲突或快照损坏返回明确错误。
- `order-content-edit.service.ts` 负责：
  - 手工单内容编辑的版本校验、稳定顺序锁与服务端重算
  - `manual_applied` 库存差量扣减/回补与商品、SKU 可还原流水
  - `legacy_none` 无库存编辑提示，以及 revision、审计的事务内写入
- `report.service.ts` 负责：
  - 库存、标签销售、金蝶、散客、出库流水等报表类型
  - 字段定义、分页查询、导出 Excel
  - 部门单与散客单字段差异兜底
  - 库存预览与 Excel 导出按当前且启用的 SKU 汇总 `currentStock`、`preOrderedStock`；仅当商品没有当前 SKU 时回退商品主表

## 关键状态/字段/快照

- 商品榜有“合并 / 细分规格”两种维度：合并模式只按 `item.productId` 分组，名称取商品主表 `product_name`；
  细分模式追加 `item.productNameSnapshot` 分组。两种模式的 Top N 都在 SQL 聚合完成之后才截断，
  因此合并数量恒等于该商品全部规格数量之和。
- 手工出库明细独立保存可空的 `sku_id`、`sku_code_snapshot`、`spec_text_snapshot`；新单按当前启用 SKU 固化快照，
  历史无 SKU 行保持 `NULL` 且继续按旧口径展示。O2O 历史名称已内嵌规格时，打印展示不会重复追加规格文本。
- 部署后新建手工单固定为 `manual_applied`，数量必须为正整数；创建时在同一事务按商品、SKU 稳定顺序加锁，以 `currentStock - preOrderedStock` 校验可用量，同时扣减商品与 SKU `currentStock` 并写可还原流水。SKU `defaultPrice` 仅用于预填，人工价格不会回写 SKU 默认价；单 current SKU 商品仍保留商品主价回写，多 current SKU 商品不回写商品主价。
- `manual_applied` 手工单允许软删除和恢复，但仍承载库存影响，因此禁止永久删除；避免在订单和明细物理消失后留下无法核对的库存扣减。升级前 `legacy_none` 单据不影响库存，仍沿用既有永久删除治理。
- 历史手工单迁移为 `legacy_none`，允许编辑内容但明确不追溯库存；O2O 核销正式单迁移/创建为 `o2o_preapplied` 并锁定内容。详情通过 `PATCH /api/orders/:id/content` 携带 `expectedVersion` 和完整明细，服务端重算金额与库存差额；`GET /api/orders/:id/revisions` 提供永久修订时间线。
- 饼图分片截断到 Top 8 后会补一片“其他”，占比分母是区间全量总额，卡片总额等于区间真实总额。
- 趋势分桶在服务层用**本地时区**日期键完成，不使用任何数据库方言日期函数；
  趋势查询必须走 `getMany()` 的实体水合，不能用 `getRawMany()`——原始结果会跳过驱动的时间归一化，
  SQLite 会返回不带时区标记的 UTC 字符串并被重新按本地时间解析，导致整段趋势串日。
- 统计区间统一左闭右开（`>= 起始日 00:00`、`< 结束日次日 00:00`），结束日整天都被覆盖；右边界通过本地日历加一天计算，不使用固定 24 小时毫秒数，确保夏令时切换日仍准确落在次日 `00:00`。区间上限 366 天。
- 合并只允许目标父单与本次全部来源单处于同一服务器本地统计日；同日不同时刻可以合并，跨日首次合并和向既有父单追加都返回资格冲突。该门禁保证父单汇总后仍留在原统计日，避免 `merged` 来源被过滤后把当日/当月数据迁移到父单日期。

- 出库单主字段：`showNo`（永久不可改的系统兼容键）、`businessNo`（列表/详情/打印/报表展示且允许受控修订）、`editVersion`、`orderType`、`customerDepartmentName`、`customerName`、`totalQty`、`totalAmount`、`isDeleted`。
- 历史修订统一走 `POST /api/orders/amendments/preview` 与 `POST /api/orders/amendments`。前者无副作用，后者在事务内重新锁单、校验版本和永久占号并整批提交；部门/散客分别使用 `hyyzjd`/`hyyz` 命名空间，同命名空间批量重编以最大确认号作为最终游标。
- 类型修订会按目标类型校验并清理领用字段；修订弹窗不得扩展商品明细、库存扣减或库存流水能力。订单永久删除后，业务号占用和 revision 仍保留。
- 详情明细以快照优先：`productNameSnapshot`、`skuCodeSnapshot`、`specTextSnapshot`、`lineAmount`，避免商品后来改名或改规格影响历史单据展示。
- 正式出库单的预览、浏览器打印与 PDF 在前端展示层按有效 `productId + skuId` 聚合；历史无 `skuId` 行继续按 `productId` 兼容聚合。同组完整名称/规格快照和不同备注均保留，缺失 `productId` 的历史行逐条展示。该规则不改库存、核销、删除恢复或审计语义，也不回查当前商品覆盖历史快照。
- O2O 关联出库单通过 `idempotencyKey` 前缀识别，与预订单删除可见性联动。
- 订单合并治理：父单保持原 `showNo`/`businessNo`，来源单状态改为 `merged`，父单状态保持 `active`；复制来源明细时保存 `sourceOrderId`、`sourceOrderUuid`、`sourceOrderItemId` provenance，父单金额/数量重新汇总，`inventoryImpact` 固定为零且不写库存流水。
- `order_merge_operation` 保存操作 UUID、幂等键、请求哈希、目标版本、来源 ID 列表、原因、操作者和完整结果快照；`order_merge_relation` 保存一条“父根 -> 来源原单”关系及父/来源业务号快照。来源只能有一个父根，关系为一层，父/来源/操作外键采用 `RESTRICT`。
- 列表只分页返回 active 根父单；关键字命中来源子单时仍返回父根一次并附带完整子树，详情通过父子关系跳转。Dashboard 与出库报表按 active 口径统计，不重复计入 merged 来源子单。
- 创建、删除、恢复和永久删除审计统一记录操作当时的 `businessNo`，同时保留 `targetCode=showNo` 作为内部兼容与跳转键；工作台近期动态优先展示审计快照中的业务单号。
- 报表字段集不是页面随意拼接，而是后端字段定义驱动。

## 权限与安全边界

- Dashboard 依赖 `dashboard:view`。
- 出库开单依赖 `orders:create`，查看历史依赖 `orders:view`，删除依赖 `orders:delete`，编辑合规位依赖 `orders:update`；内容编辑独立依赖 `orders:edit`，仅授予既有拥有 `orders:update` 的管理员和操作员角色。
- 订单合并预览/提交依赖 `orders:merge`，默认授予 admin；来源 `merged` 单不能独立删除、恢复或永久删除，任一合并成员永久删除均由服务端关系门禁阻断；父单软删除/恢复时同步整个 O2O 合并组可见性。
- 永久删除属于高风险操作，除了权限外还要求永久删除密码。

## 常见异常与排查顺序

1. 工作台数字不对：先查 `dashboard.service.ts` 的过滤条件是否排除了软删除单据。
2. 趋势图或排行榜和列表不一致：查 Dashboard 与报表是否使用了不同时间范围或订单类型过滤。
3. 商品榜出现同名不同色重复条目：查 `getAnalytics` 的 `productSpecMode` 是否被切到 `spec`，
   以及是否有人重新给商品榜查询加回了 `addGroupBy('item.productNameSnapshot')`。
4. 榜单/饼图和下钻抽屉对不上：查抽屉是否透传了当前 `appliedFilter`（区间 + 订单类型 + 规格快照）。
3. 出库单重复提交：查 `idempotencyKey` 是否缺失或前端重复生成策略异常。
4. 删除后流水号回拨异常：查 `order.service.ts` 的 `recalibrateCurrentFromOccupancy()`。
5. O2O 关联出库单删除后预订单看不见/看得见不对：查关联可见性同步逻辑。
6. 合并后列表重复或统计重复：查根分页、来源子单搜索和 Dashboard/report 的 `status=active` 过滤。

## 验证与回归关注点

- 出库链路至少回归：单/多 SKU 新建、历史无 SKU 详情、手工单内容编辑与并发版本冲突、revision 时间线、打印/PDF 规格、报表规格、人工价格覆盖、软删、恢复、永久删、合规标记编辑。
- 手工出库 SKU 专项：`npm --prefix backend run order:manual-sku:verify`。
- 内容编辑专项：`npm --prefix backend run order:content-edit:verify`。
- 工作台回归：四宫格、区间筛选（按日/按月、跨月跨年）、饼图、趋势、商品榜合并/细分、Top N 切换、钻取、近期动态文案。
- 工作台自动化回归命令：`npm --prefix backend run dashboard:analytics:verify`。
- 报表回归：报表类型切换、字段列头、分页、导出文件名。
- 库存口径专项：`npm --prefix backend run reports:inventory:verify`。该脚本使用唯一临时 SQLite，核对商品服务、预览和实际 Excel，并覆盖标签、自定义字段、500 行跨批次及真实库存生命周期。
- 订单合并专项：`npm --prefix backend run order:merge:verify`（真实 SQLite 事务、幂等、父子治理、同本地统计日门禁、根分页/子搜索、Dashboard/report 口径、权限与回滚）和 `npm --prefix backend run order:merge:migration-fixture:verify`（045 迁移补齐、关系约束与快照）。
- 合并前端静态/状态专项：`npm run verify:order-merge-frontend`；MySQL 结构契约运行 `npm --prefix backend run verify:mysql:schema-contract`，双连接并发与 pending return 阻断运行 `npm --prefix backend run verify:db:concurrency`。
