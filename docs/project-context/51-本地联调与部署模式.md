# Y-Link 本地联调与部署模式

## 适用范围

- 适用于本地联调、onebox、双容器云端部署和外置 MySQL 部署模式的区分。
- 适用于定位“当前机器为什么连到这个数据库、哪个容器负责前端/后端/上传目录”的问题。

## 最后核对来源

- `start-local-dev.ps1`
- `compose.cloud.yml`
- `compose.mysql.yml`
- `compose.onebox.yml`
- `compose.onebox.mysql.yml`
- `.env.onebox.example`
- `Dockerfile.onebox`
- `docker/nginx/onebox.conf`
- `docker/nginx/configure-proxy-boundary.sh`

## 真实入口

- 本地联调脚本：`start-local-dev.ps1`
- SQLite/双容器云端部署：`compose.cloud.yml`
- 外置 MySQL 双容器部署：`compose.mysql.yml`
- 单容器 onebox：`Dockerfile.onebox`
- 渐进式 Onebox（默认 SQLite、以后可选安装 MySQL）：`compose.onebox.yml` + `compose.onebox.mysql.yml`
- SQLite -> MySQL 自动迁移隔离验收：
  `docker/compose.verify-db-migration.yml` + `npm run verify:db:migration`

## 前端链路

- 本地联调只启动一个 Vite 开发服务器，同时承载管理端和客户端页面。
- onebox 模式下前端静态资源由 Nginx 提供，并代理后端接口与健康检查。
- 双容器模式下前端容器的健康检查同时覆盖静态页和 `/health` 代理链路。

## 后端链路

- 本地联调脚本会：
  - 清理旧 PID 和端口占用
  - 生成本次后端临时 env
  - 拉起前后端
  - 等待 `/health` 和前端端口就绪
  - 输出当前实际数据库摘要与来源
- `compose.cloud.yml` 默认仍可使用 SQLite，并要求挂载 `/app/data` 与 `/app/uploads`。
- `compose.mysql.yml` 只起应用容器，数据库由外置 MySQL 提供。
- `compose.mysql.yml` 会透传 MySQL 连接池、连接/获取/空闲超时、等待队列上限和慢查询阈值；多副本部署时需要按
  `副本数 × DB_POOL_SIZE` 计算总连接数，不能让应用连接耗尽 MySQL `max_connections`。
- 外置或云 MySQL 不在同一可信内网时，应开启 `DB_SSL_MODE=verify-full`（校验证书链与主机名，`DB_HOST` 须与证书一致，私有 CA 用 `DB_SSL_CA` 指向容器内挂载的 PEM 文件）；`required` 只加密不校验证书，仅作过渡。该设置同样作用于运行时覆盖与 SQLite→MySQL 迁移目标库，开启后迁移目标也必须支持 TLS。默认 `disabled` 保持现有内网直连行为。
- `Dockerfile.onebox` 在同一容器内打包前端、后端与 Nginx。
- `compose.onebox.yml` 默认只启动 `ylink` 并使用 SQLite；正式启用时叠加 `compose.onebox.mysql.yml`，只追加同一私有网络中的 MySQL，
  不会启动第二套应用。数据切换必须继续走管理端自动迁移，不能直接改 env 后指向空库。
- Onebox 连接 Linux 宿主机 MySQL 时使用 `host.docker.internal`（Compose 已映射 `host-gateway`）；连接远程 MySQL 时使用容器可达的 DNS/IP，禁止把数据库端口无边界暴露到公网。
- `compose.verify-db-migration.yml` 不是生产部署模板：
  - 固定 `mysql:8.4` 和独立库 `y_link_migration_verify`；
  - MySQL 不发布宿主机端口，onebox 只发布随机选择的 `127.0.0.1` 端口；
  - 两个服务只加入 `internal` 验收网络，自动任务目标固定为 `mysql:3306`；
  - 每次命令使用唯一 Compose project，创建 3 个 project 隔离卷，结束时执行
    `docker compose down --volumes`；
  - 管理员与 MySQL 验收密码每次随机生成，只注入当前脚本进程，不写入仓库、日志或 CI Secret。

## 关键状态/字段/快照

- `/health` 是公开存活与维护状态接口，只返回 `status/maintenance`，不再输出数据库摘要；确认实际数据库模式应使用管理员运行时覆盖/数据库性能接口，不以 env 或公开健康响应猜测。
- onebox 和 cloud compose 都需要考虑上传目录持久化，否则图片会随容器丢失。
- onebox Nginx 只直出 `/uploads/products/`（公开商品图）；其余 `/uploads/*` 一律代理给 Node。`uploads/client-feedback`（客户私有附件）与 `uploads/.tmp`（未校验临时文件）绝不能由 Nginx 按磁盘路径直出，附件只能经 `/api/client-feedback/attachments/:id` 与 `/api/customer-service/attachments/:id` 鉴权读取；`npm run verify:onebox:uploads` 会断言该边界。
- 运行时数据库覆盖存在时，部署模式和 `.env` 看到的值不一定等于真实生效数据库。
- onebox 自动迁移要求 `/app/data` 持久化。SQLite、迁移任务、备份、维护状态、
  cutover marker 与运行时覆盖必须位于同一持久化根目录，否则容器重启后无法继续验证或回退。
- 敏感配置加密主密钥 `secrets/data-encryption.key` 同样位于数据根目录（onebox 为 `/app/data`），首次启动自动生成，启动日志 `DATA ENCRYPTION` 行回显来源与密钥 ID（不含密钥本身）。**备份数据库时必须同时备份该文件**（SQLite 物理备份结果会回显配套密钥 ID，但不会把密钥写进备份目录；只恢复数据库、缺少配套密钥文件时服务会以 `DATA_ENCRYPTION_KEY_MISSING` 进入救援模式而不是生成新密钥，恢复密钥文件后重启即可）；分体 MySQL 部署也要持久化后端 `/app/data`，否则重建容器会生成新密钥，已保存的验证码网关与飞书配置需要重新录入。多个后端实例共用一个 MySQL 时，改用 `Y_LINK_DATA_ENCRYPTION_KEY` 注入同一密钥。
- SQLite Onebox 只允许一个应用进程且数据库文件必须位于本地持久化磁盘；需要第二副本或持续并发写时先迁移 MySQL。
- 后端镜像（`backend/Dockerfile`、`backend/Dockerfile.mysql`）与 onebox 入口脚本默认 `UV_THREADPOOL_SIZE=8`：libuv 线程池由 scrypt、sharp、SQLite 驱动与文件读写共用，默认 4 线程在登录洪水时会饿死数据库查询。该变量必须在进程启动前由环境设置（Node 加载 ESM 入口时就可能已初始化线程池，代码内设置无效）；非容器部署需在启动命令的环境中自行设置。
- Node 服务端硬化（`backend/src/runtime/http-server-hardening.ts`，业务与救援服务共用）：`keepAliveTimeout` 65 秒（大于 onebox Nginx 上游空闲超时 50 秒，避免复用已关闭连接产生 502）、`headersTimeout` 66 秒、`requestTimeout` 120 秒（只约束接收请求阶段，抵御慢速请求攻击，不影响导出与 SSE）、`maxHeadersCount` 100。监听地址取 `Y_LINK_LISTEN_HOST`（默认 `0.0.0.0`，只接受 IP 或 localhost）；onebox 入口脚本默认 `127.0.0.1`，外部只能经 Nginx 进入，无法绕过边缘限流与请求体上限。不使用通用 `HOST` 变量，避免被 shell 自动设置的主机名误读。
- onebox Nginx 通过 `upstream ylink_backend`（`keepalive 32`、`keepalive_timeout 50s`）复用到 Node 的长连接，所有代理 location 均需 `proxy_http_version 1.1` 与清空 `Connection` 头，`npm run verify:onebox:uploads` 会断言。分体部署的 Nginx 保留变量式延迟解析，暂不改为 upstream。
- 三套 Nginx（`onebox.conf`、`default.conf`、`default.conf.template`）的边缘约束口径一致：登录区 12 次/分（管理端与客户端登录、两步验证第二步共用）、验证码区 30 次/分、敏感匿名区 30 次/分（注册、发码、找回校验与重置）、`/api/` 通用区每 IP 50 次/秒（突发 500），每 IP 同时处理中的请求 ≤256（`limit_conn`，空闲长连接不计）。超限返回 429、请求体超限返回 413，均为 JSON（`data.reason` 为 `EDGE_RATE_LIMITED` / `EDGE_PAYLOAD_TOO_LARGE`，429 附 `Retry-After: 5`）。请求体默认上限 1m，认证入口 64k，商品图上传、反馈附件、商品导入、教职工名录导入放宽到 11m（此前默认 1MB 会拦截 >1MB 的 GIF 与导入文件；Nginx 限制的是含 multipart 边界与字段头的整个请求体，必须略高于后端 10MB 文件上限）。校园网等大量用户共用出口 IP 时，按实际并发调大 `ylink_api_general` 的 rate/burst 与 `limit_conn`；容量型 DDoS 必须由上游 CDN/高防承担，单机限流只能削减单一来源的洪水。改动后运行 `node scripts/verify-web-edge-security.mjs`，有 Docker 时用现有镜像执行 `nginx -t`。
- MySQL 切换后产生第一笔新业务写入，旧 SQLite 即成为历史快照；禁止清除覆盖后直接回旧库。
- Onebox 迁移前要在 `.env` 中确定 MySQL 连接池与超时参数；运行时覆盖只保存目标库连接信息，迁移后连接池仍读取容器环境变量。
- 全新空 MySQL 可仅在第一次启动临时使用 `DB_SYNC=true` 创建当前完整实体结构，健康后必须立即改回 `false`；
  存量 MySQL 禁止开启同步，应停写、备份并按版本号执行未应用的增量 SQL。
- `backend/sql/001_init_schema.sql` 只代表历史基础结构，不能单独作为当前版本完整初始化；本轮至少按顺序执行
  `034_high_concurrency_indexes.sql`、`035_o2o_idempotency_business_sequence.sql`、`036_notification_outbox.sql`。
  `036` 会合并历史重复收件箱的已读状态并删除重复行，升级顺序必须是“备份 -> 停止所有应用/通知 Worker -> `034/035/036` -> 启动新版本”，并为索引 DDL 预留窗口；商城缓存继续复用 `030/034` 索引，本轮没有额外 catalog 结构脚本。
- 自动迁移开关 `Y_LINK_AUTOMATIC_DB_MIGRATION_ENABLED` 是部署门禁：
  - 普通分体后端未显式设置时保持关闭，因为它不保证按退出码 `75` 自动重启；
  - onebox 入口默认设置为 `true`，因为它具备计划重启与持久化恢复链路；不允许自动切换时可显式设为 `false`；
  - 验收 Compose 固定开启，但它的 internal 网络和临时卷不能复用为正式环境。

## 反向代理、HTTPS 与独立救援页

- 后端的 `Y_LINK_TRUST_PROXY` 填 Node 的直接反向代理地址，例如 onebox 内部默认 `127.0.0.1,::1`，或分体 Compose 的前端固定地址；只能填写明确 IP/CIDR，不能填布尔值、跳数或 `0.0.0.0/0`。
- Nginx 的 `Y_LINK_TRUSTED_EDGE_PROXIES` 仅填写实际 TLS 终止边缘的 IP/CIDR。配置脚本只让列出的边缘决定转发协议，未列出的请求继续按当前连接协议处理。
- 对公网 HTTPS，边缘必须真实终止 TLS 并传递可信协议；可按部署需要设置 `Y_LINK_FORCE_SECURE_COOKIES=true`，并保留有效的 `Y_LINK_HSTS_MAX_AGE_SECONDS`。对仅局域网 HTTP，保持 `Y_LINK_FORCE_SECURE_COOKIES=false` 可兼容普通 Cookie 会话，但不得开放救援凭证。
- `rescue.html` 是独立 Vite 入口，Nginx 通过 `/database-rescue` 映射该页面并设置 `no-store`；它不加载普通 App、Store 或 HTTP 模块。后端进入救援态时，页面只可调用独立 `/api/database-rescue` 控制面。
- 容器内需要轮换指定任务的救援凭证时，仅运行：`node /app/backend/dist/runtime/database-rescue-cli.js rotate-credential <taskId>`。该命令不接受路径、SQL、Shell 或连接参数；其 stdout 是唯一明文交付通道，不能重定向到普通日志。
- 管理端两步验证应急重置（唯一管理员丢失认证器且恢复码用尽，或数据加密密钥丢失）：在后端运行目录执行 `node dist/runtime/admin-mfa-reset-cli.js <用户名>`（容器内为 `/app/backend`，本地开发为 `npm --prefix backend run admin-mfa:reset -- <用户名>`）。只接收用户名，按当前运行配置连库删除该账号的两步验证记录并写审计。开启两步验证的部署必须保证服务器时间与 NTP 同步。
- MySQL 部署升级到含两步验证的版本时需要 `backend/sql/057_admin_mfa.sql`（已在 `DB_AUTO_MIGRATE` 白名单内）；未开启自动迁移时须先手工执行，否则启动自检会阻断并指向该脚本。SQLite 由启动期结构同步自动建表。

## 权限与安全边界

- 部署文档中的环境变量不应写入真实密码。
- onebox 和 compose 都依赖后端对敏感配置的脱敏日志策略。
- 外部服务和 Webhook 仍由后端安全校验，而不是部署层兜底。

## 常见异常与排查顺序

1. 本地启动成功但页面数据不对：先看联调脚本输出的数据库摘要和 `/health`。
2. 线上图片 404：查 `/app/uploads` 是否持久化挂载。
3. 双容器前端健康检查失败：查前端是否既能访问根路径又能代理 `/health`。
4. onebox 能打开首页但接口异常：查 Nginx 代理和后端启动是否都成功。
5. 切到 MySQL 后行为还像 SQLite：查运行时覆盖和实际 `/health` 摘要。
6. 自动迁移 API 返回未启用：检查 `Y_LINK_AUTOMATIC_DB_MIGRATION_ENABLED=true` 是否注入 onebox，而不是向普通后端容器随意开放。
7. 自动迁移后容器没有重启：检查 onebox 是否保留退出码 `75`，并确认部署平台的重启策略没有被设为 `no`。
8. 验收命令在本机直接失败：先看输出属于 Docker CLI 缺失、Compose v2 缺失还是 daemon 未启动；这三类都属于真实阻断，不允许当作通过。
9. 外置 MySQL 首启提示缺表：确认目标是否真为空库；空库可在隔离首次启动阶段临时启用 `DB_SYNC=true`，存量库只能核对并补跑缺失的编号增量脚本。
10. 存量 MySQL 提示缺少 `business_sequence`、幂等列或 Outbox 索引：这是启动契约主动阻断；备份并停止全部应用/通知 Worker 后执行 `035`、`036`，不要在仍有旧实例写入时开启自动迁移。
11. 出现 `RESCUE`：确认访问为可信 HTTPS 或容器本地，再按独立救援操作说明使用任务凭证；不要将普通局域网 HTTP 当作救援本机访问，也不要手工删除 override、maintenance、cutover 或恢复意图文件。

## 验证与回归关注点

- 改本地联调脚本后回归：启动、停止、日志输出、数据库摘要、前端地址。
- 改 compose/onebox 后回归：容器健康检查、图片访问、管理端登录、客户端商城。
- 改自动迁移、运行时覆盖、维护屏障或 onebox 重启链路后，运行：

```bash
npm run verify:db:migration
```

- 可执行负向场景：

```bash
Y_LINK_DB_MIGRATION_SCENARIO=wrong-connection npm run verify:db:migration
Y_LINK_DB_MIGRATION_SCENARIO=old-version npm run verify:db:migration
Y_LINK_DB_MIGRATION_SCENARIO=wrong-charset npm run verify:db:migration
Y_LINK_DB_MIGRATION_SCENARIO=insufficient-permissions npm run verify:db:migration
Y_LINK_DB_MIGRATION_SCENARIO=non-empty-target npm run verify:db:migration
Y_LINK_DB_MIGRATION_SCENARIO=duplicate-task npm run verify:db:migration
Y_LINK_DB_MIGRATION_SCENARIO=content-tamper npm run verify:db:migration
Y_LINK_DB_MIGRATION_SCENARIO=execution-interruption npm run verify:db:migration
Y_LINK_DB_MIGRATION_SCENARIO=verifying-emergency-rollback npm run verify:db:migration
Y_LINK_DB_MIGRATION_SCENARIO=failure-rollback npm run verify:db:migration
```

- PowerShell 可使用：

```powershell
$env:Y_LINK_DB_MIGRATION_SCENARIO='wrong-connection'
npm run verify:db:migration
Remove-Item Env:Y_LINK_DB_MIGRATION_SCENARIO
```

- `content-tamper`、`execution-interruption`、`verifying-emergency-rollback`、`failure-rollback` 的确定性故障注入仅在
  `APP_PROFILE=verify-db-migration` 且 `Y_LINK_DB_MIGRATION_E2E=true` 的隔离环境启用；
  生产 profile 无法触发这些门禁。
