# Y-Link 验证脚本与高风险操作

## 2026-11 外发、工作流与 Onebox 加固批次

- 本节是验收清单，不代表命令已运行。整体实现及一次独立深审、集中修正后统一执行；禁止逐文件全测。源码快照和实际结果另存本批隔离证据。
- 后端 `security:safe-http:verify` 覆盖 DNS 停滞/迟到、持续小包、多跳共享预算、半包/error/aborted/close、收口竞态、资源清理、响应上限及 compat/strict 跳转矩阵；`notification:outbox:verify` 用独占 SQLite 和停滞 DNS 验证真实投递失败、维护租约释放及验证码 504/502 映射。
- 根目录 `node --test scripts/verify-action-workflow-pins.test.mjs scripts/verify-node-workflow-pins.test.mjs scripts/verify-dependency-audit-scope.test.mjs scripts/verify-onebox-identity.test.mjs` 检查官方固定 SHA/release、权限、checkout 凭据、Node 固定点、依赖闭包与身份切换失败即停。非 Mobile 工作流的 Action SHA 已由官方仓库 GitHub tag/commit 核实，Mobile 工作流不属当时的修改范围。现行 Mobile 工作流也纳入同一官方 Action SHA/release 与 checkout 凭据持久化检查。
- `verify:security-updates` 将根 Web 和后端各一次包含 dev 的官方 npm 审计投影到各自生产闭包与构建增量，排除独立 Mobile 专属根。公告用本次 npm CLI 自带的官方 semver 匹配每个安装版本并重新归属严重度，不沿用包名聚合的跨版本 severity 或升级建议；公告引用、锁定版本或范围缺失均失败。生产 high/critical 继续阻断；构建工具漏洞单独报告，审计失败明确失败；Mobile 原有非阻断报告保留，不计入本批通过。构建闭包按安装路径定义，不宣称最终业务可达性。
- 实际镜像使用 `Y_LINK_VERIFY_IMAGE`、`Y_LINK_VERIFY_PLATFORM=linux/amd64|linux/arm64` 与独占 `Y_LINK_VERIFY_EVIDENCE_DIR`：原生依赖检查 `verify-onebox-native-runtime.mjs`；`verify-onebox-http-runtime.mjs` 分别设 `Y_LINK_VERIFY_ONEBOX_NON_ROOT=false/true`，核实后端/补充组、Nginx/supervisor、SQLite WAL、密钥、HTTP/上传/SSE/边缘限制及 SIGTERM；`verify-onebox-permission-refusal.mjs` 仅创建自有旧式 root 私有卷，验证拒绝启动且 owner/mode/密钥内容不变。
- 本批优先本机原生平台，不要求注册 binfmt 或自动增加双架构矩阵。`verify-onebox-corrupt-override.mjs` 使用独占新卷，在非 root 模式下验证损坏但可读的 runtime override 稳定返回救援 503、不初始化业务库或密钥、不重启循环，并正常处理 SIGTERM。
- `verify:db:migration` 增加 `Y_LINK_VERIFY_ONEBOX_NON_ROOT=true` 的同一隔离矩阵入口，onebox 夹具同样以 node 执行。至少覆盖 success（退出码 75 重启及 MySQL 生效）、failure-rollback、corrupted-cutover-marker（独立救援）与 cutover-cancel-persistence-failure；最后一项必须覆盖 PREPARED 取消恢复重放，断言实际数据源为 SQLite、源数据摘要保持、恢复次数恰为一次及数据快照一致，不只检查 env；不复用业务库/卷。
- `npm --prefix backend run supplier:portal:verify` 在独占 SQLite/数据目录中验证启用但未上架、两种库存非零 SKU 的供货方提交及两种详情均脱敏，另一供货方 404，管理员与库管保持真实库存，核验后物理库存正确增加而预占不变；响应成本序列化保护继续生效。
- 本批统一清单还包括完整 `verify:performance`（内含前端 build）、后端 build、编码、docker-base、路由契约、security:hardening/http-boundary 及受影响认证专项、隔离 MySQL/Redis 和本机原生平台真实镜像。产物预算 4780/870/325/1195 KB、cold 3000ms 不变；历史 Windows 冷启动失败单列。另一架构未测须如实披露，不继承旧批次双架构成本或注册特权 binfmt；本地 Scout 产出 SBOM/漏洞证据，不改发布工作流现有 provenance/SBOM 合并策略。

## 适用范围

- 适用于选择验证脚本、判断文档/配置/代码改动最少要跑哪些验证，以及识别高风险操作边界。
- 适用于提交前和交付前的验证决策。

### 正式扫描后续补丁的验证入口隔离

- 认证/SSE、入库删除、库存/报表、YZ 商品、订单内容/合并/手工 SKU、编号治理、客户端核心链路、阿里云验证码、两条数据库并发入口和发布回归共 15 个独立入口，在应用模块导入前创建独占空 `ENV_FILE`、随机 profile/数据根，关闭 Redis 并跳过数据库运行时覆盖；连接、prepare 或同步结构前核对实际数据库类型/路径或 MySQL 连接目标，以及上传、备份、密钥等持久路径。此边界只适用于验证脚本，不改变正常应用配置优先级。
- MySQL 临时库为随机独占名称，给随机后缀预留长度，创建时拒绝已有库；清理前重新核对服务器 UUID 与持久所有权标记。标记放独占伴随控制库，业务目标仍保持真正为空，不修改生产空库/保留目标/结构校验以迁就测试。创建失败是真实失败，不以 environment 状态返回成功；所有权标记失败时保留现场，不能猜测目标归属后删除。认证/SSE 的显式 MySQL 模式要求 loopback、高位端口和 `AUTH_SSE_VERIFY_MYSQL_CONFIRM_TEST_SERVER=true`；发布回归继续使用原有高位端口/确认门禁。
- 认证/SSE 的确认 flag 只确认测试服务器，不授权任何已有库：raw 入口还必须由本进程排他 CREATE 成功，并在同步前重新证明服务器/所有权和业务库确实为空。后端目录下 `node --import tsx scripts/auth-sse-mysql-isolation-verify.ts` 使用真实专属 MySQL 检查带额外列/哨兵的已有库被拒绝且不变、合法新库可运行并仅清理自身；探针覆盖创建失败不得 DROP。
- `npm --prefix backend run security:verification-isolation:verify` 使用专造 SQLite 哨兵和 MySQL 连接替身，逐个启动 raw 入口并在首次真实连接前停止，检查污染 `ENV_FILE`、有效 runtime override、60 字符库名、创建失败、所有权丢失、异常清理和 schema worker 的继承边界。它证明入口保护，不代替真实 MySQL/业务验收。
- `npm --prefix backend run security:client-account-write:verify` 的真实服务回归覆盖撤单、打印及评价：生命周期先提交拒绝旧请求且无订单/库存/合规/评价/审计写入；业务先持账号锁则允许合法完成，随后注销，检查锁序不死锁。默认使用独占 SQLite；MySQL 仅接受已核对所有权的测试 fixture。`security:inventory-csv:verify` 验证差异报告每个 CSV 单元格的公式中和，JSON 输出和只读行为不变。
- 上述是新增回归入口与待执行清单，未代表本批后续补丁已经验收；统一结果须绑定最终源码快照，受影响的旧入口结果不能复用为新代码通过。

### 手动持续冻结与固定 npm 后续统一验收

- `npm --prefix backend run verify:db:migration:manual` 使用真实隔离 SQLite/MySQL，覆盖两种手动切换、完整响应后仍在途 Promise/worker 排空、冻结后停用/撤会话拒绝、并发 run/switch/cancel、marker/override/task/补偿/启动终态写盘故障、历史同数量库存/账号/会话变化、无 taskId 强验收与保留目标选项。每个 case 独立进程，不用这些服务测试代替真实 Onebox。
- 同一手动专项还覆盖删锁后真实子进程终止、维护文件删除失败后的启动前幂等补偿，普通 failed 无证明仍拒绝；另通过真实本机 HTTP 代理验证普通 HTTP 不得取明文凭证但可在本地准备后执行，可信 HTTPS 协议路径可签发并执行。页面原处理器测试分别覆盖 HTTP 本地准备提示、HTTPS 暂存顺序和401/403失败停止，不把代理协议头测试称为真实浏览器 TLS 验收。
- 手动专项的 `schema-worker-cancel` 使用自有子进程夹具验证建表进程在输出后仍可取消，检查取消意图、快照引用和旧失败写入，并在释放迁移锁失败后启动新进程完成取消。`schema-worker-shutdown` 覆盖真实子进程退出、停机后的准入拒绝及启动预检识别原冻结。`failed-cleanup-crash` 和 `failed-cleanup-rescue-race` 分别覆盖失败收尾先认领和独立救援先接受的交错。`npm --prefix backend run security:http-boundary:verify` 覆盖正常期先鉴权、冻结期同任务准入和 16 KB 预读上限。
- 手动专项验证超长诊断字段在源库与原始物理备份中保留，工作快照、JSON 与 MySQL 使用适配值，并覆盖目标预检失败、再次执行、取消、人工切换、重启强校验与工作快照被修改时的拒绝。
- `npm --prefix backend run verify:db:migration:resume` 通过本机 HTTP、独占 SQLite 和控制文件覆盖 `202` 响应后租约释放、手动占有期间接续调度、旧任务与新持久锁隔离、启动恢复及冻结后的故障终态。目标故障由夹具注入，对真实 MySQL 的验证仍由迁移专项覆盖。
- `Y_LINK_DB_MIGRATION_SCENARIO=manual-switch|manual-prepared-switch|manual-cancel|manual-failure-rollback|manual-corrupt-override`（每次选择一项）配合 `npm run verify:db:migration`，在专属镜像、卷、internal 网络中验证人工重启、持续只读、取消、SQLite 救援及真实数据源；至少覆盖默认和非 root 两模式的正常流程，以及非 root 的受影响故障/恢复矩阵。
- `node --test scripts/verify-manual-migration-ui.mjs scripts/verify-customer-service-reply-race.mjs scripts/verify-pinned-npm.test.mjs backend/scripts/audit-pinned-npm.test.mjs` 覆盖实际页面处理器的异步归属、救援凭证先保存后冻结、固定工具完整性/阶段契约和 global npm 按实际版本归属公告；测试库/连接替身不表示真实 MySQL/镜像通过。
- 统一冻结和新增范围独立复核后，最终源码仍须运行一次 `npm run verify:performance`（含前端 build）、后端 build、编码及受影响业务/迁移专项。r4 的产物/启动结果不能证明本轮页面、迁移模块与 npm 工具变更；Windows 冷启动失败单列，预算不变，不为重复证明而反复跑整套。
- 所有受影响 Node 镜像阶段实际构建并核实当前固定工具修订、npm/npx 及原生构建；最终运行镜像执行实际 global npm 物化闭包审计及 Scout/SBOM。官方npm11.21.2与拟派生修订11.21.2-ylink.1分开绑定；moderate 仍报告，high/critical 阻断，下载/完整性/审计失败明确失败；不改宿主 npm、不改 Mobile，不扩展为发行版或 SQLite 驱动替换。

## 固定 SQLite 原生绑定的必要验收

- 窄契约入口为 `node --test backend/scripts/pinned-sqlite.test.mjs`，覆盖源完整性拒绝、旧版本/错误SourceID/能力裁剪拒绝、动态SQLite依赖拒绝、自有项目/环境与驱动锁边界，以及Onebox验钥工具分层。它不编译、不连接业务库，不能替代真实原生验证。
- 真正重建后必须用固定Node22.23.5运行 `node backend/scripts/verify-pinned-sqlite.mjs --project=<隔离后端目录> --static`，确认实际sqlite3模块返回3.54.1和批准SourceID，且无旧系统/预编译或新动态SQLite库旁路；Linux使用readelf、Windows使用现有dumpbin。所有数据库验证必须沿用独占ENV_FILE/数据/密钥与owned数据库边界。
- Windows x64隔离原型只证明本机静态链接/API/编译能力；Linux x64/arm64、真实WAL/备份恢复、旧库隔离升级、SQLite→MySQL强校验、Onebox两模式及最终镜像SBOM/CVE均须按真实输入变化纳入统一验收。不能用新CLI或Node自带SQLite版本代替应用绑定证据，也不能用旧镜像证明新原生制品。
- 默认backend安装已接包级postinstall，真实SQLite文件打开前由共用驱动入口验证内存引擎；编译/带密钥Sonar的ignore-scripts不提供原生运行保证。CI的node_modules缓存须签入固定源码策略/构建脚本/工具修订，命中后仍执行实际绑定校验，不能以单独rebuild sqlite3或旧锁命中替代。
- 直接入口还包括后端目录的 `node --import tsx --test scripts/verified-sqlite-driver.test.ts` 与根目录 `node --test backend/scripts/runtime-termination.test.mjs`：分别覆盖实际驱动身份/失败不缓存/MySQL不加载，以及普通启动失败、清理期间终止意图和75。它们尚待本批统一运行，合成生命周期屏障不冒称真实镜像信号验收。
- 此处新增原生制品需要Windows x64及Linux amd64/arm64必要验证，与上方历史加固批次只要求本机平台的范围不同；没有能力时明确受阻，不自动注册特权binfmt。native更新影响实际数据库执行输入，不能仅凭业务TS未改复用旧迁移通过；未受影响的路由/权限/HTTP等检查按代码、依赖、配置和环境映射复用。
- 系统库的源认证、正式包构建/安装身份、ABI和正常输入兼容回归分别记录。此前平台拦截的原生安全测试保持原样、不重写/执行，未完成的libblkid边界回归也不能由普通输入测试替代；本批不得因此声称原生安全证明完整。最终镜像保留全部旧Scout规则到实际包/补丁/副本的映射，包括low/medium/未定。

## GitHub CI 与本地验收边界

- Pull Request 的必要检查仍只有名为 `verify` 的一项：文本编码、Web/后端构建、出站 HTTP DNS 与重定向安全验证、MySQL 结构契约、YZ 通用 SKU 编码体系与 YZ 建库 Excel 导入验收、路由权限契约和写事务闸门。
- `.github/workflows/sonarcloud.yml` 在 PR 与 `main` 上运行 SonarCloud 分析：无密钥的 `coverage` 作业用 Node 内置 V8 覆盖率执行后端隔离 SQLite 验证（含 WebAuthn 直接登录、启用、兼容、负向、旧库升级和 MFA）、共享包单测，以及前端认证、订单、条码和原始 SFC 行为验证。普通 TS/JS 源码使用 Node LCOV；Node 22 内置 Vue source-map 转换已证实会误报未执行处理器、漏报已执行处理器，因此 SFC 和同一条码编译产物中的 helper.ts 改由 `scripts/v8-sfc-coverage.mjs` 根据原始 V8 ranges、实际 source-map segment 保守映射 DA/BRDA。条码 helper 的直接 TS 测试报告仍独立保留，合并时相同源码只计算一次代码行，并保留真实零命中分支。

- `.github/workflows/security-updates.yml` 在指向 `main` 的 PR、`main` push 和每天北京时间 09:00 运行 `npm run verify:security-updates`，状态名 `security-updates`，读取 lockfile、不安装依赖。它对照 nodejs.org 发行索引检查全部 Node 版本固定点（四个 Dockerfile 默认镜像、`docker-publish.yml` 构建参数、迁移验证 Compose、工作流 `node-version`、Mobile `engines` 与 `eas.json`）：精确版本低于所在主版本线最新安全版本或主版本已 EOL 即失败；本项目所有 setup-node 步骤还必须显式固定为 Onebox 同一补丁版本，拒绝浮动主版本、错误补丁、表达式或缺失声明。setup-node 默认优先匹配 Runner 本地缓存，不能假定 `node-version: 22` 会取得最新补丁。同时审计根 Web 与后端的生产依赖，high/critical 一律失败，包括需大版本升级或暂无修复的情况，并输出具体依赖路径。Mobile workspace 在完整隔离 workspace 中单独审计，尚未上线只输出结果，但失败或未执行不得记为零漏洞。要让它阻断合入，需在 `main` 的 Ruleset 中加为必要检查。
- Node 镜像固定到精确补丁版本（如 `node:22.23.5-bookworm-slim`），而不是浮动的 `node:22-bookworm-slim`：浮动标签无法让 CI 发现线上镜像落后，固定版本被检查报红后升级 Dockerfile 会触发 `docker-publish.yml` 重建镜像。升级时全部固定点一起改，`npm run verify:docker-base-image` 会校验 Dockerfile 与发布流水线一致。

- `main` 与发布标签的镜像发布仍由 `.github/workflows/docker-publish.yml` 执行；它属于交付流程，不是 Pull Request 必要检查。`main` 上只改 `docs/**`、`spec/**` 或根目录 Markdown 的提交不触发镜像发布（镜像内容不变，`latest`/`main`/`sha-*` 标签也不会为该提交刷新）；发布标签与手动触发不受路径过滤影响。
- 后端 lockfile 保留 `prebuild-install@7.1.3` 及以上约束；旧版 `napi-build-utils@1` 的N-API识别问题是历史安装故障，不作为接受旧预编译引擎的理由。现在SQLite运行安装必须执行受控源码重建及实际内存引擎门禁，构建工具缺失就失败，不静默回退3.44.2；安装耗时按新构建输入实测，不能继续引用旧预编译约6秒作为保证。

## 前端链路

- 文档、中文文本或规则文件改动后，最低应跑 `npm run verify:text-encoding`。
- 前端核心改动后，最低应跑 `npm run build`。
- 大版本、路由重构、核心链路重构后，应跑 `npm run verify:performance`。

## 后端链路

- 后端 TypeScript 改动后，应跑 `npm --prefix backend run build`。
- 出站 HTTP 的 DNS 回调、地址族或重定向安全边界改动后，应跑 `npm --prefix backend run security:safe-http:verify`；它覆盖 `all: true` 地址数组与单地址回调、IPv4/IPv6 `family` 筛选、完整 DNS 解析集合的内网/保留/映射回环地址拒绝，以及重定向时重新解析和跨源敏感请求头剥离。
- Redis 票据、限流风控、Pub/Sub 总线、后台任务租约、startup lock 或多实例前置校验改动后，应跑 `npm --prefix backend run redis:integration:verify`：针对真实 Redis 验证票据加密与一次性消费、限流与风控、跨实例广播、租约与降级语义。需要本机 Docker（自动拉起临时 Redis）或通过 `REDIS_URL` 指向可丢弃的 Redis；严禁对生产 Redis 运行。
- MySQL 连接会话参数、连接池空闲回收或事务重试相关改动后，应跑 `npm --prefix backend run mysql:session-resilience:verify`：用临时 `mysql:8.4` 容器验证池连接会话参数、锁等待超时以可重放错误失败、空闲连接被回收、持锁失联事务在空闲上限后被回滚并释放行锁（约 1.5 分钟）。需要本机 Docker，或通过 `VERIFY_MYSQL_HOST/PORT/USER/PASSWORD` 指向可丢弃的库；严禁对生产库运行。
- SQLite 事务协调器、`DataSource.transaction/query` 或 `QueryRunner` 接管逻辑改动后，应跑：
  - `npm --prefix backend run transaction-coordinator:verify`
  - `npm --prefix backend run task8:verify`
- SQLite -> MySQL 自动迁移、维护只读屏障、运行时切换或 onebox 重启改动后，必须跑：
  - `npm run verify:db:migration:timeout`
  - `npm run verify:db:migration`
- 权限、路由、鉴权、安全边界改动后，应补充：
  - `npm --prefix backend run task2:route-contract:verify`
  - `npm --prefix backend run security:hardening:verify`
- O2O、订单、入库、通知等已有专项验证脚本时，应优先使用对应脚本而不是只跑构建。
- Issue #70 汇总修复专项（均使用独立临时 SQLite；Windows 本机 Temp 路径含中文时需把 `TEMP`/`TMP` 指向纯英文目录，否则 SQLite 打不开）：
  - `npm --prefix backend run o2o:order-pool:verify`：订单池分栏服务端计数、退货交叉、倒序分页、越界收敛、筛选口径与新单基准。
  - `npm --prefix backend run audit:catalog:verify`：源码审计动作全部登记类别、LIKE 转义、类别筛选、默认隐藏通知内部记录与导出一致。
  - `npm --prefix backend run notification:event-log:verify`：外发审计真实结果、共用 Webhook 不漏写、重试不重复计数、按事件聚合、筛选与详情脱敏。
  - `npm --prefix backend run order:source-doc:backfill:verify`：出库单来源快照历史回填精确清理、幂等与 046 迁移契约。
- Issue #71 订单合并专项应按层执行：
  - `npm --prefix backend run order:merge:verify`：隔离 SQLite 真事务，核心脚本以独立 `America/New_York` 子进程覆盖春秋夏令时切换日，验证 preview 无副作用、幂等稳定快照、父/来源状态和 provenance、关系/操作/审计、服务器本地统计日门禁、跨日回滚、Dashboard/report 本地日历右边界、根分页与来源搜索、权限、冲突回滚及删除治理；其中串行执行 O2O 合并场景。

- 依赖文件或 Node 版本固定点变化时，应在本地执行 `npm run verify:security-updates`（脚本显式使用 npm 官方源审计，本机默认镜像源不提供审计接口）。修复依赖漏洞时优先 `npm update <包> --package-lock-only` 定向升级，不要对根目录整体 `npm audit fix`：根 lockfile 含 Mobile workspace，整体修复会连带升级 expo 并触发 peer 冲突；稀疏检出缺少 `apps/` 时 npm 还会把 Mobile 依赖整段删出 lockfile。

## Web 安全与救援验证

- 救援启动最小验证可运行 `node --import tsx backend/scripts/database-rescue-startup-verify.ts`；它覆盖数据库不可达、cutover marker 损坏与 runtime override 损坏时只启动受限控制面的行为。
- 后端已提供可用 `npm --prefix backend run <别名>` 调用的专项别名：`verify:db:rescue:control`、`verify:db:rescue:protocol`、`verify:db:rescue:startup`、`verify:db:rescue:digest`、`verify:db:write-freeze` 与 `verify:db:migration:sequence`。它们分别覆盖控制文件、恢复重放、受限启动、SQLite 摘要、写冻结和包含 `sqlite_sequence` 历史高位/空洞的迁移序列口径。

- 敏感数据防泄露与抗 DDoS / 爆破加固统一运行 `npm --prefix backend run security:data-leak-ddos:verify`（约 40 秒）。脚本按阶段起子进程，各自使用独立临时 SQLite、数据目录与工作目录：

- 高风险操作包括但不限于：
  - 永久删除订单或送货单
  - 注销、恢复或永久删除系统账号/客户端账号

  - 影响库存、订单状态、客服消息流转的服务层改动
- 这些场景除了通过权限，还应在说明中明确写出风险面和验证结果。

## 权限与安全边界

- 永久删除类操作不仅要有权限，通常还要求永久删除密码。
- 数据库迁移、运行时覆盖切换、系统级配置变更通常要求管理员角色。
- `verify:db:migration` 的目标库固定为隔离 Compose 内部的
  `mysql:3306/y_link_migration_verify`，脚本不读取 `DB_HOST/DB_NAME/DB_PASSWORD`
  作为迁移目标；这是防止误连外部或生产库的硬边界。
- 验收编排只使用 project 隔离临时卷，命令结束后删除。需要保留正式数据时必须使用正式部署卷，
  不能把验收 Compose 当作备份或迁移工具。
- 通知与验证码通道配置属于外部联动安全边界，不应视为普通表单改动。

## 常见异常与排查顺序

1. 文档改了但字符乱码：先跑 `npm run verify:text-encoding`。
2. 前端看似没问题但构建挂了：跑 `npm run build`，重点看路由和类型引用。
3. 后端接口能跑但权限边界错了：跑后端路由契约和安全验证。
4. 性能回归没被发现：检查是否遗漏 `npm run verify:performance`。
5. 高风险操作说明不完整：核对是否单独说明了数据库、通知、订单、库存或权限风险。
6. `verify:db:migration` 输出 Docker 严格阻断：Docker CLI、Compose v2 或 daemon 任一不可用都应非零退出，不能捕获后强制返回成功。
   Docker 三项前置检查各有 12 秒硬超时，daemon 无响应时必须明确失败，不能无限等待。
7. 迁移脚本只看到了覆盖文件：这不构成通过；必须观察容器 `RestartCount` 增长、`/health` 显示 MySQL 实际生效，并完成内容一致性对比。
8. 救援控制文件损坏：应保留现场并使用受限控制面诊断；删除 runtime override、cutover marker 或恢复意图后反复重启不属于恢复步骤。

## SQLite -> MySQL 严格验收入口

默认成功闭环：

```bash
npm run verify:db:migration
```

命令使用真实 onebox 镜像和真实自动任务 API，按顺序断言：

1. `docker --version`、`docker compose version`、`docker info` 全部可用；
2. MySQL 固定为 8.4，独立库字符集为 `utf8mb4`，MySQL 不发布宿主机端口；
3. onebox 初始 `/health` 明确运行在 SQLite；
4. 管理员真实登录，获取 Cookie/CSRF；隔离夹具命令按实体外键顺序补齐全部应用表，并强制确认每张表非空；
5. `POST /api/data-maintenance/db-migration/automatic-tasks` 返回 HTTP `202` 与脱敏任务；
6. 维护期 `/health.maintenance.readOnly=true`，普通写入返回 HTTP `503`、`code=50301`；
7. onebox 容器 `RestartCount` 实际增加；
8. 任务终态为 `succeeded`，维护态解除，`/health` 显示运行时覆盖 MySQL 已生效；
9. 直接查询隔离 MySQL，确认 8.4、utf8mb4、业务表与数据存在；
10. 任务强校验明细必须覆盖全部非空实体表，逐表结构、行数、SHA-256、约束与自增序列全部通过；重新登录后 `export/json.tables` 内容也必须完全一致；
11. 无论成功失败都销毁本次 Compose project、internal 网络与临时卷。

负向场景通过同一 npm 命令切换环境变量：

- `wrong-connection`：错误内部主机也必须先返回 HTTP `202` 与任务 ID，再由后台状态机进入 `failed`；不得触发 onebox 重启，SQLite 保持生效且内容不变；
- `old-version`：真实启动 MySQL 8.0.15，确认最低版本门禁在任何迁移写入前阻断；
- `wrong-charset`：把隔离目标库改为 `latin1`，确认字符集门禁阻断；
- `insufficient-permissions`：撤销目标账号 `ALTER`，确认权限清单检查在 DDL 探针前阻断且目标库仍为空；
- `non-empty-target`：预置 guard 数据后也必须先返回 HTTP `202`，随后任务进入 `failed`；不得清理目标既有数据或触发切换；
- `duplicate-task`：并发提交第二个自动任务，确认全局锁或维护写屏障拒绝重复任务且首任务继续完成；
- `content-tamper`：保持目标行数不变并确定性篡改内容，确认规范化 SHA-256 不一致会禁止切换；
- `execution-interruption`：建表后确定性退出进程，确认 onebox 拉起后仅清理本任务所有结构并自动续跑；
- `verifying-emergency-rollback`：MySQL 重启后在 `verifying` 阶段执行紧急回退，确认取消意图先持久化、任务不会被 finalizer 覆盖为成功，SQLite 重启自检后再解除维护；
- `failure-rollback`：在隔离验收 profile 下确定性注入两次 MySQL 启动失败，验证 onebox 连续重启、SQLite 自动回退、维护解除和原库内容一致。
- `overlong-diagnostic-text`：向源 SQLite 注入含多字节字符的超长 UA，并临时制造业务列超长：预检须对业务列给出 `error` 阻断、对 UA 列仅给出 `warning`；迁移成功后 MySQL 中 UA 须按字符精确截断到 255 且 SHA-256 与预期一致；
- `binlog-trigger-restricted`：运行时关闭目标库 `log_bin_trust_function_creators`，确认触发器探针在冻结写入前以可操作提示阻断，目标库保持为空。

默认 success 还会断言迁移目标库存在 044 的两个 `account_lifecycle_event` 只追加触发器。

迁移矩阵只证明数据搬得对，不证明迁移后的 MySQL 上业务能正常读写。为此 `npm --prefix backend run release:verify` 支持 MySQL 模式：设置 `RELEASE_REGRESSION_MYSQL_PORT`（10000–65535，仅连 `127.0.0.1`）、`RELEASE_REGRESSION_MYSQL_CONFIRM_TEST_SERVER=true`，以及可选的 `RELEASE_REGRESSION_MYSQL_USER`/`RELEASE_REGRESSION_MYSQL_PASSWORD`。脚本在随机新库中按自动迁移同一路径建表：先由建表子进程 initialize，再补建必需触发器，然后由子进程 verify。之后走 MySQL 生产启动自检，并跑完同一套全功能 HTTP 回归，最后删除随机库并回查。只能指向独立测试实例，例如临时 `mysql:8.4` 容器，不得指向业务库。

数据库迁移矩阵不再由每个 Pull Request 自动执行。涉及迁移实现时，开发者应在本地对默认成功闭环和受影响的负向场景逐一执行并留存结果；任何 API `404`、未知状态、密码泄露、维护屏障缺失、容器未重启、MySQL 未生效或内容不一致都属于验收失败。
