# Y-Link 验证脚本与高风险操作

## 适用范围

- 适用于选择验证脚本、判断文档/配置/代码改动最少要跑哪些验证，以及识别高风险操作边界。
- 适用于提交前和交付前的验证决策。

## 最后核对来源

- `package.json`
- `backend/package.json`
- `AGENTS.md`
- `.github/workflows/verify-db-concurrency.yml`
- `backend/src/services/database-migration.service.ts`
- `backend/src/services/data-maintenance.service.ts`
- `backend/src/routes/o2o.routes.ts`
- `backend/src/routes/inbound.routes.ts`
- `backend/src/runtime/database-rescue-control.ts`
- `.local-dev/security-hardening/` 下的本轮验证报告

## 真实入口

- 前端/根验证脚本：`package.json` 的 `scripts`
- 后端验证脚本：`backend/package.json` 的 `scripts`
- GitHub Pull Request 必要检查：`.github/workflows/verify-db-concurrency.yml`
- 高风险动作门禁：永久删除密码、管理员角色、迁移/导入导出接口权限

## GitHub CI 与本地验收边界

- Pull Request 只自动运行名为 `verify` 的必要检查：文本编码、Web/后端构建、出站 HTTP DNS 与重定向安全验证、MySQL 结构契约、路由权限契约和写事务闸门。
- Docker 全镜像构建、Onebox 升级、数据库迁移矩阵、数据库并发和依赖审计不再自动占用 GitHub 托管 Runner，应在本地按改动范围执行。
- Mobile 工作流只在 `apps/mobile/**`、`packages/**`、`.npmrc` 或 Mobile 专用检查脚本变化时触发；Web、后端或根锁文件变化不应单独触发 Mobile 构建。
- `main` 与发布标签的镜像发布仍由 `.github/workflows/docker-publish.yml` 执行；它属于交付流程，不是 Pull Request 必要检查。

## 前端链路

- 文档、中文文本或规则文件改动后，最低应跑 `npm run verify:text-encoding`。
- 前端核心改动后，最低应跑 `npm run build`。
- 大版本、路由重构、核心链路重构后，应跑 `npm run verify:performance`。

## 后端链路

- 后端 TypeScript 改动后，应跑 `npm --prefix backend run build`。
- 出站 HTTP 的 DNS 回调、地址族或重定向安全边界改动后，应跑 `npm --prefix backend run security:safe-http:verify`；它覆盖 `all: true` 地址数组与单地址回调、IPv4/IPv6 `family` 筛选、完整 DNS 解析集合的内网/保留/映射回环地址拒绝，以及重定向时重新解析和跨源敏感请求头剥离。
- SQLite 事务协调器、`DataSource.transaction/query` 或 `QueryRunner` 接管逻辑改动后，应跑：
  - `npm --prefix backend run transaction-coordinator:verify`
  - `npm --prefix backend run task8:verify`
- SQLite -> MySQL 自动迁移、维护只读屏障、运行时切换或 onebox 重启改动后，必须跑：
  - `npm run verify:db:migration:timeout`
  - `npm run verify:db:migration`
- 权限、路由、鉴权、安全边界改动后，应补充：
  - `npm --prefix backend run task2:route-contract:verify`
  - `npm --prefix backend run security:hardening:verify`
- O2O、订单、入库、通知等已有专项验证脚本时，应优先使用对应脚本而不是只跑构建。
- 商品库存展示、库存报表或 Excel 库存列变更后，应运行 `npm --prefix backend run reports:inventory:verify`；它使用唯一临时 SQLite，真实解析流式 Excel，并验证 SKU 汇总、标签分页、500 行批次、库存生命周期和只读边界。
- 依赖文件变化时，应在本地执行 `npm audit --omit=dev` 与 `npm --prefix backend audit --omit=dev`；审计依赖外部 registry，不作为每个 PR 的稳定必过门禁。

## Web 安全与救援验证

- Web 安全、路由、Cookie、代理与救援控制面改动，除构建外应运行相关后端契约，例如 `npm --prefix backend run security:findings:verify`、`npm --prefix backend run task2:route-contract:verify`、`npm --prefix backend run write-transaction:contract:verify`，以及受影响的认证/O2O 验证。
- 救援启动最小验证可运行 `node --import tsx backend/scripts/database-rescue-startup-verify.ts`；它覆盖数据库不可达、cutover marker 损坏与 runtime override 损坏时只启动受限控制面的行为。
- 后端已提供可用 `npm --prefix backend run <别名>` 调用的专项别名：`verify:db:rescue:control`、`verify:db:rescue:protocol`、`verify:db:rescue:startup`、`verify:db:rescue:digest`、`verify:db:write-freeze` 与 `verify:db:migration:sequence`。它们分别覆盖控制文件、恢复重放、受限启动、SQLite 摘要、写冻结和包含 `sqlite_sequence` 历史高位/空洞的迁移序列口径。
- 认证、HTTP 代理和业务安全边界可分别运行 `npm --prefix backend run security:auth-depth:verify`、`npm --prefix backend run security:http-boundary:verify`、`npm --prefix backend run security:business-boundary:verify`；附件清理链路使用 `npm --prefix backend run feedback:attachment-cleanup:verify`。安全改动应按触及边界选择这些别名，而不是只跑通用构建。
- 根 `npm run verify:performance` 的隔离后端冷启动以 `tsx src/index.ts`、新建 SQLite、`DB_SYNC=true` 为口径，从子进程 spawn 后到首次 `/health` 返回成功计时，预算固定为 `3000ms`。健康探测每 `50ms` 重试，并在 JSON 报告记录最后失败和首次成功观测时刻；该改动只减少轮询量化误差，不改变起点、健康判定或预算。外层工具进程即使返回 0，仍必须以脚本内性能子项的真实语义结果为准。
- 2026-09-06 安全加固整合时的隔离 `npm run verify:performance` 曾通过全部子项；冷启动为 `1692.65 / 3000ms`，构建总产物为 `4198.37 / 4200 KB`。随后新增迁移连接测试和完成态显示，提交前生产构建测得总产物 `4203.36 / 4200 KB`，仅总量超预算 `3.36 KB`，首屏指标通过；运行时子项本次未继续执行，历史通过不能替代当前完整性能门禁。详见 `docs/Web安全加固验收记录.md` 的提交前补充验证。Task 6 注册测量必须在计时前加载测试 provider，避免把测试模块首次导入误计为注册服务耗时。
- 根依赖锁的 Web-only 审计结果与后端生产审计为 0；Mobile workspace 在全量安装口径仍有 19 项审计告警。三种范围不同，报告时不得合并或写成同一结论。
- 当前安全加固在普通分支 `codex/web-security-hardening` 上整理，用户已授权本地提交；本地提交不构成已合入、已发布或全部验证完成的声明。

## Docker 交付镜像本地构建

涉及 Dockerfile、Compose、Nginx、Onebox 或后端运行时依赖时，在本地执行：

```bash
docker build --file Dockerfile --tag ylink-frontend:local .
docker build --file backend/Dockerfile --tag ylink-backend-sqlite:local backend
docker build --file backend/Dockerfile.mysql --tag ylink-backend-mysql:local backend
docker build --file Dockerfile.onebox --tag ylink-onebox:local .
npm run verify:onebox:smoke
```

这些命令只生成本地镜像，不登录镜像仓库、不推送镜像，也不应连接正式数据库。

## 关键状态/字段/快照

- 高风险操作包括但不限于：
  - 永久删除订单或送货单
  - 数据库迁移与运行时切库
  - JSON 导入导出
  - 通知外发与验证码通道修改
  - 影响库存、订单状态、客服消息流转的服务层改动
- 这些场景除了通过权限，还应在说明中明确写出风险面和验证结果。

## 权限与安全边界

- 永久删除类操作不仅要有权限，通常还要求永久删除密码。
- 数据库迁移、运行时覆盖切换、系统级配置变更通常要求管理员角色。
- `verify:db:migration` 的目标库固定为隔离 Compose 内部的
  `mysql:3306/y_link_migration_verify`，脚本不读取 `DB_HOST/DB_NAME/DB_PASSWORD`
  作为迁移目标；这是防止误连外部或生产库的硬边界。
- 验收编排只使用 project 隔离临时卷，命令结束后删除。需要保留正式数据时必须使用正式部署卷，
  不能把验收 Compose 当作备份或迁移工具。
- 通知与验证码通道配置属于外部联动安全边界，不应视为普通表单改动。

## 常见异常与排查顺序

1. 文档改了但字符乱码：先跑 `npm run verify:text-encoding`。
2. 前端看似没问题但构建挂了：跑 `npm run build`，重点看路由和类型引用。
3. 后端接口能跑但权限边界错了：跑后端路由契约和安全验证。
4. 性能回归没被发现：检查是否遗漏 `npm run verify:performance`。
5. 高风险操作说明不完整：核对是否单独说明了数据库、通知、订单、库存或权限风险。
6. `verify:db:migration` 输出 Docker 严格阻断：Docker CLI、Compose v2 或 daemon 任一不可用都应非零退出，不能捕获后强制返回成功。
   Docker 三项前置检查各有 12 秒硬超时，daemon 无响应时必须明确失败，不能无限等待。
7. 迁移脚本只看到了覆盖文件：这不构成通过；必须观察容器 `RestartCount` 增长、`/health` 显示 MySQL 实际生效，并完成内容一致性对比。
8. 救援控制文件损坏：应保留现场并使用受限控制面诊断；删除 runtime override、cutover marker 或恢复意图后反复重启不属于恢复步骤。

## SQLite -> MySQL 严格验收入口

默认成功闭环：

```bash
npm run verify:db:migration
```

命令使用真实 onebox 镜像和真实自动任务 API，按顺序断言：

1. `docker --version`、`docker compose version`、`docker info` 全部可用；
2. MySQL 固定为 8.4，独立库字符集为 `utf8mb4`，MySQL 不发布宿主机端口；
3. onebox 初始 `/health` 明确运行在 SQLite；
4. 管理员真实登录，获取 Cookie/CSRF；隔离夹具命令按实体外键顺序补齐全部应用表，并强制确认每张表非空；
5. `POST /api/data-maintenance/db-migration/automatic-tasks` 返回 HTTP `202` 与脱敏任务；
6. 维护期 `/health.maintenance.readOnly=true`，普通写入返回 HTTP `503`、`code=50301`；
7. onebox 容器 `RestartCount` 实际增加；
8. 任务终态为 `succeeded`，维护态解除，`/health` 显示运行时覆盖 MySQL 已生效；
9. 直接查询隔离 MySQL，确认 8.4、utf8mb4、业务表与数据存在；
10. 任务强校验明细必须覆盖全部非空实体表，逐表结构、行数、SHA-256、约束与自增序列全部通过；重新登录后 `export/json.tables` 内容也必须完全一致；
11. 无论成功失败都销毁本次 Compose project、internal 网络与临时卷。

负向场景通过同一 npm 命令切换环境变量：

- `wrong-connection`：错误内部主机也必须先返回 HTTP `202` 与任务 ID，再由后台状态机进入 `failed`；不得触发 onebox 重启，SQLite 保持生效且内容不变；
- `old-version`：真实启动 MySQL 8.0.15，确认最低版本门禁在任何迁移写入前阻断；
- `wrong-charset`：把隔离目标库改为 `latin1`，确认字符集门禁阻断；
- `insufficient-permissions`：撤销目标账号 `ALTER`，确认权限清单检查在 DDL 探针前阻断且目标库仍为空；
- `non-empty-target`：预置 guard 数据后也必须先返回 HTTP `202`，随后任务进入 `failed`；不得清理目标既有数据或触发切换；
- `duplicate-task`：并发提交第二个自动任务，确认全局锁或维护写屏障拒绝重复任务且首任务继续完成；
- `content-tamper`：保持目标行数不变并确定性篡改内容，确认规范化 SHA-256 不一致会禁止切换；
- `execution-interruption`：建表后确定性退出进程，确认 onebox 拉起后仅清理本任务所有结构并自动续跑；
- `verifying-emergency-rollback`：MySQL 重启后在 `verifying` 阶段执行紧急回退，确认取消意图先持久化、任务不会被 finalizer 覆盖为成功，SQLite 重启自检后再解除维护；
- `failure-rollback`：在隔离验收 profile 下确定性注入两次 MySQL 启动失败，验证 onebox 连续重启、SQLite 自动回退、维护解除和原库内容一致。

数据库迁移矩阵不再由每个 Pull Request 自动执行。涉及迁移实现时，开发者应在本地对默认成功闭环和受影响的负向场景逐一执行并留存结果；任何 API `404`、未知状态、密码泄露、维护屏障缺失、容器未重启、MySQL 未生效或内容不一致都属于验收失败。

截至 2026-09-06，真实 Docker 迁移矩阵的 18 个场景均已通过，且本任务创建的容器与卷均已清理。其中包括默认 success、带 30 个实体序列空洞的 success、`failure-rollback`、`verifying-emergency-rollback` 与 `corrupted-cutover-marker`；后者确认独立网页、业务 API `503`、稳定救援无重启循环，以及容器本地凭证经真实 HTTP nonce/幂等回退和精确一次审计。

## 验证与回归关注点

- 文档/规则改动：`npm run verify:text-encoding`
- 前端结构改动：`npm run build`
- 后端结构改动：`npm --prefix backend run build`
- SQLite 事务协调器改动：`npm --prefix backend run transaction-coordinator:verify` + `npm --prefix backend run task8:verify`
- 数据库自动迁移/onebox 切换：`npm run verify:db:migration`
- 权限/路由/安全改动：后端契约与安全验证脚本
- 大型重构：性能验证
