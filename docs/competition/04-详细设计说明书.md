# Y-Link——智能库存与订单协同管理系统详细设计说明书

> 文档版本：竞赛冻结基线版；事实基线：`b149f945ad4702bc56487955ac2e2a0b8e359e2a`；产品范围：管理端 Web、客户端 Web、Node.js 后端、SQLite/MySQL 数据层及一体化部署。
> 范围说明：本说明书不把原生移动端写入当前参赛产品能力；文中接口、字段、状态与并发策略均以冻结提交中的代码、SQL 迁移和验证脚本为准。

## 1. 文档目的与设计原则

本说明书把概要设计继续下沉到路由、服务、实体、事务和页面交互层，重点回答四个问题：一次业务操作从哪个页面和接口进入；哪些对象在同一个事务中改变；并发或重复请求到来时如何保持库存和订单一致；失败后系统保留什么状态、如何审计与恢复。

系统设计遵循以下原则。

1. **库存只有一套业务真值。** `currentStock` 表示物理库存，`preOrderedStock` 表示 O2O 已预占但尚未核销的数量，可售量始终为两者之差。页面缓存、购物车数量和订单快照都不能替代服务端库存。
2. **写链路先鉴权、再锁参与者、后锁业务对象。** 管理端与客户端使用不同会话；关键事务先复核账号仍然有效，再按稳定顺序锁商品、SKU 或订单，避免账号停用与业务写入之间出现时间窗口。
3. **单据、库存、流水、审计同成同败。** 创建订单后扣库存、核销后生成正式出库、入库核验后增加库存等动作均在同一数据库事务中完成。事务回滚时，不留下“有单无账”或“有账无单”。
4. **幂等不等于忽略参数。** O2O 下单、扫码库存单据等链路既保存请求键，也保存归一化内容摘要。同一个键、同一个内容才允许重放；同一个键承载不同内容返回冲突。
5. **数据库能力差异由基础设施层吸收。** SQLite 使用有界单写协调，MySQL 使用行锁和连接池并发；业务服务保持相同不变量，不依赖前端串行点击。
6. **历史单据保留快照。** 商品名称、价格、规格、部门、工号、客户、开单人等会随主数据变化的内容写入订单快照，历史凭证不因主数据修改而失真。
7. **权限在服务端闭环。** 菜单隐藏只改善交互，不构成安全控制；接口通过身份、角色、细粒度权限、CSRF、高风险口令和频控组合门禁。

## 3. 前端详细设计

### 3.1 路由、壳层与页面进入顺序

`src/router/routes.ts` 集中定义路径、标题、目标端、角色/权限提示、菜单可见性、`keepAlive`、预热目标和 `viewKey`。同一业务工作台的不同入口可共享 `viewKey`，避免切换菜单时重复创建重型页面。`src/router/index.ts` 在导航前按目标端初始化相应会话，只接受本地安全重定向；无权限时转向当前账号可访问的首个页面。

```text
点击菜单或客户端底栏
        │
        ▼
读取 route.meta（目标端、权限、viewKey、预热目标）
        │
        ├─ 尚未初始化会话 ──> 调用 /me 恢复服务端会话
        │
        ├─ 未登录 ─────────> 登录页（仅保留安全站内 redirect）
        │
        ├─ 无权限 ─────────> 首个可访问页面或拒绝页
        │
        └─ 允许 ───────────> Layout → Suspense → KeepAlive 页面
```

管理端 `AppLayout.vue` 从路由元数据生成侧栏，维护全局加载、在线心跳、维护横幅和最大 8 个页面缓存；客户端 `ClientMainLayout.vue` 提供响应式 Web 壳层、底部导航和最大 3 个页面缓存。客户端退出登录时同时清除目录、购物车和订单等用户域缓存，防止同一浏览器切换账号后串读。

### 3.2 Store 与 API 协作

管理端认证 Store 只在本地保存无敏感的用户快照和过期提示，真实会话位于 HttpOnly Cookie；客户端认证 Store 同理，且与管理端 Cookie/CSRF 命名空间分开。`src/api/http.ts` 负责：

- 管理写请求注入管理端 CSRF，客户端写请求注入客户端 CSRF；
- 维护模式下在浏览器侧提前阻断普通写请求，但保留恢复所需入口；
- 客户端 CSRF 缺失时仅执行一次 `/client-auth/me` 刷新并重试，避免无限循环；
- 收到未认证或账号失效响应时清理对应会话并引导重新登录；
- 将后端业务错误归一化为页面可显示的信息，不暴露堆栈和敏感配置。

客户端目录 Store 以服务端为真值，本地缓存用于快速首屏，缓存有效期为 5 分钟。购物车按用户隔离，加入数量上限取商品可售量与限购量的较小值；目录刷新发现库存变化时，不静默删除或缩减用户已经选择的数量，而是在结算前形成不可变选择快照并明确报告冲突。这样既不篡改用户意图，也不会把旧缓存提交成订单事实。

### 3.3 共享 UI 组件与交互

| 组件/模式 | 交互职责 | 关键边界 |
|---|---|---|
| `BizResponsiveDataCollectionShell` | 桌面表格与窄屏卡片切换，统一骨架、空态、分页 | 数据量大时关闭逐项动画，并尊重 reduced motion |
| `UnifiedScanDialog` | 相机授权、扫码区域、手动输入与扫描结果回传 | 只提供输入能力；产品、SKU、盲盘字段仍由接口裁剪 |
| `TabbedWorkbenchPage` | 在一个工作台内承载列表、录入、历史等页签 | 复用 KeepAlive，避免重复拉取和丢失筛选状态 |
| 详情抽屉/对话框 | 查看订单快照、流水、审批或异常原因 | 打开时单独请求详情，关闭时清理临时敏感输入 |
| 请求状态壳层 | loading、empty、error、retry | 旧请求不得覆盖新筛选结果；错误必须可重试或可解释 |

## 4. 后端装配、事务与审计

### 4.1 路由装配与运行时

`backend/src/index.ts` 是轻量预检入口，动态启动业务运行时。正常应用在 `backend/src/app.ts` 中装配：健康检查、公共认证、客户端认证、客户端反馈和 O2O 公共/客户端路由；管理业务统一位于 `/api` 保护链之后。数据库救援接口在普通写屏障之前单独装配，但只在严格的恢复条件下可用。

管理端保护链为：解析管理会话 → 复核身份 → Cookie 写请求校验双提交 CSRF → JSON 解析 → 业务路由。客户端路由使用独立中间件：若请求显式带 `Authorization`，该凭据独立决定结果，不在失败后悄悄回退 Cookie；Web 客户端 Cookie 写请求同样需要客户端 CSRF。

### 4.2 route-service-entity 分工

- **Route**：声明路径和权限，解析 Zod DTO、路径参数与查询参数，提取 IP/UA 等请求元数据，调用服务并输出标准响应。
- **Service**：实施状态机、事务、锁顺序、幂等、库存校验、审计和领域错误；禁止由路由拼接多步数据库写入。
- **Entity/Repository**：保存关系、快照、软删除、唯一约束和检查约束；数据库约束作为并发下最后一道防线。
- **Middleware**：认证、CSRF、权限、角色、上传安全、频控、维护模式和统一错误处理。

### 4.3 事务协调与数据库差异

系统通过统一事务入口传播 `EntityManager`。嵌套服务复用当前事务，避免内部服务另开事务提前提交。SQLite 写入进入有界单写队列，队列满或等待超时返回可重试的 503；MySQL 不做全局串行，而是依靠事务、稳定锁序和行级悲观锁并发执行。代码还拒绝业务层发送原始 `BEGIN/COMMIT/ROLLBACK` 控制 SQL，避免破坏统一边界。

锁序的一般规则是：账号 → 业务单据 → 商品（ID 升序）→ SKU（ID 升序）。同一批对象先归一化、去重、排序，再加锁。MySQL 使用 `pessimistic_write`；SQLite 因单写协调不依赖行锁语义，但仍保持相同顺序，便于两种数据库得到一致行为。

### 4.4 异常与审计

参数错误返回 400；未认证返回 401；权限不足返回 403；状态冲突、库存不足、幂等键载荷冲突返回 409；SQLite 写队列或暂时性数据库压力可返回 503。服务端日志与响应不输出会话凭据、密码、数据库连接密钥或完整第三方地址。

审计实体记录动作、操作者、目标、结果、结构化详情、IP 和 User-Agent。关键业务审计与业务变化尽量同事务写入：事务成功才存在成功审计；事务失败由统一错误/安全日志记录失败上下文。权限中间件对越权尝试另行记录，以保留未进入业务事务的拒绝事件。

### 5.2 核心实体字段

| 实体 | 关键字段 | 设计含义 |
|---|---|---|
| `BaseProduct` | `productCode`、名称、默认价、折扣、O2O 状态、限购、`currentStock`、`preOrderedStock` | 商品聚合与默认展示；预占不得超过物理库存 |
| `BaseProductSku` | `skuCode`、规格、售价、折扣、条码、成本、库位、库存、当前/启用/推荐标志 | 实际可售规格；成本字段不进入普通序列化结果 |

| `BizInboundOrder` | 展示号、核验码、供应方、状态、预计到达、核验/取消快照、软删除 | 供应方提交与管理端核验凭证 |
| `BizOutboundOrder` | UUID、展示号、业务号、状态、`inventoryMode`、幂等键、开单与客户快照 | 正式出库凭证；区分手工已扣、O2O 预扣和历史不扣模式 |
| `O2oPreorder` | 状态、取消原因/来源、业务状态、请求键/摘要、核销信息、客户/部门/取货快照 | O2O 主状态和请求幂等事实 |
| `O2oReturnRequest` | 状态、源订单状态快照、原因、处理人、退货明细 | 待审核、通过、驳回的售后子流程 |
| `InvStockDoc` | 单号、类型、请求键、内容摘要、状态、原因 | 扫码库存变动凭证，可按原数量作废 |
| `InvStocktake` | 范围、盲盘、状态、范围互斥键 | 盘点生命周期和范围占用 |

### 5.3 快照与主数据的边界

主数据用于“现在还能不能做”：商品/SKU 是否有效、库存是否足够、用户是否启用。快照用于“当时发生了什么”：下单价格、商品名称、规格、图片、客户部门、工号、出库经办人。订单列表和打印优先使用快照，不因后续改名或调价重写历史；库存校验始终回到当前受锁定的实体，不依赖快照。

## 6. 库存真值、共享记账与流水

### 6.1 库存口径

```text
物理库存 physical = currentStock
预占库存 reserved = preOrderedStock
可售库存 available = currentStock - preOrderedStock

当前商品汇总库存 = Σ（isCurrent = true 且 isActive = true 的 SKU 库存）
```

商品聚合实体 `BaseProduct` 通过数据库检查约束保证预占不大于物理库存；`BaseProductSku` 没有同类数据库检查约束，SKU 层主要依靠服务端在事务内锁定记录并校验 `currentStock - preOrderedStock`。服务层在每次扣减前同时检查 SKU 与商品聚合的可售量。停用或退役 SKU 的历史库存可被针对性纠正，但不再计入商品当前聚合。

冻结源码中的真实实现摘录（`backend/src/services/inventory-ledger.service.ts`）：

```ts
const availableOf = (entity: { currentStock: number; preOrderedStock: number }) =>
  Number(entity.currentStock) - Number(entity.preOrderedStock)
```

这段函数不是页面展示公式，而是扣减校验的服务端基础。普通出库、通用库存单和盘点完成通过共享记账服务改变物理库存；O2O 预占、核销和退货因同时维护预占与订单状态，使用各自的领域服务完成记账。不能把“共享记账”误解为所有场景都调用同一个函数，但所有场景遵守同一库存口径并写 `InventoryLog`。

### 6.2 `applyInventoryDeltas` 的处理顺序

```text
调用方已开启事务
  → 汇总同 SKU 净变化并校验安全整数
  → 锁商品，再按稳定顺序锁 SKU
  → 校验 SKU 属于商品、是否允许参与当前操作
  → 扣减方向检查 SKU.available 与 Product.available
  → 更新 SKU.currentStock
  → 仅对当前且启用 SKU 更新 Product.currentStock
  → 保存每个 SKU 的 InventoryLog 前后快照
  → 返回调用方继续保存单据/审计
```

`stockDelta` 正数表示物理入库，负数表示物理出库。该服务明确不修改 `preOrderedStock`，从而避免普通库存单误释放 O2O 预占。MySQL 下库存列使用明确的仓储更新，降低重复读事务中实体缓存造成的覆盖风险。

### 6.3 并发不变量

| 场景 | 锁与约束 | 结果 |
|---|---|---|
| 两笔普通出库同时扣同一 SKU | 同一 SKU 行锁；SQLite 单写队列 | 后获得锁者读取最新库存，不会超卖 |
| 普通出库与 O2O 预占并发 | 都按可售量检查并锁相同商品/SKU | 任一先提交，另一方基于新 `current-preOrdered` 判断 |
| O2O 核销与取消并发 | 订单状态条件更新/行锁 + SKU 锁 | 只有一个状态迁移成功，不会同时扣减和释放 |
| 已核验入库撤销与既有预占 | 撤销前检查扣回后的可售量 | 不能把物理库存扣到低于已预占数量 |
| 退役 SKU 的库存处理 | 只更新 SKU，不回写当前商品聚合 | 历史修正不污染当前规格汇总 |

## 7. 商品、SKU、标签与 O2O 展示

### 7.1 入口与调用顺序

管理端商品中心通过 `/api/products`、`/api/tags` 和 `/api/inventory/categories|locations` 完成主数据维护。页面提交商品及规格矩阵后，路由校验 DTO 和 `products:manage`，服务开启事务、锁操作者账号、锁商品及 SKU，执行差异合并并写审计。O2O 商城通过 `/api/o2o/mall/products` 与 `/api/o2o/mall/storefront` 获取经过上架、启用、当前 SKU 和库存口径过滤的展示数据。

### 7.2 SKU 矩阵更新

SKU 先按 ID 与规格组合匹配；已有 SKU 更新价格、条码、库位、图片和状态，新组合创建新 SKU，删除的组合不做物理删除，而是标记 `isCurrent=false`、`isActive=false`、取消推荐并释放条码。存在 `preOrderedStock > 0` 时不能停用或退役，避免预订单失去可核销目标。

条码和 SKU 编码全局唯一。标签打印优先使用条码，没有独立条码时可回退 SKU 编码。修改库存基线时携带 `stockBaseline`，服务端拒绝基于旧库存页面的覆盖；传入的 `preOrderedStock` 不作为普通商品编辑值采用，预占只能由 O2O 状态机改变。手工调整物理库存会留下库存流水。

### 7.3 标签与展示

标签名称和编码均唯一。创建、修改、删除在事务内执行；仍被商品引用的标签不可删除。商城只展示启用商品及当前、启用 SKU，可售量按 `currentStock-preOrderedStock` 计算；价格、折扣、规格、图片和推荐状态形成展示 DTO。公开商城响应支持缓存/ETag，但结算不信任缓存价格和库存，后端会重新读取并锁定当前实体。

### 7.4 权限与异常

- 商品读取需要 `products:view`；维护需要 `products:manage`；导入另需 `products:import`。
- 扫码查找允许商品、库存或盘点相关读取权限；`purpose=stocktake` 在服务端裁剪库存。
- 成本价只向管理权限返回；实体普通序列化主动移除 `costPrice`。
- 编码/条码冲突、旧库存基线、SKU 仍有预占、删除仍被引用标签均返回冲突，不做部分保存。

## 8. 供应方送货与核验入库

### 8.1 对象、入口和权限

供应方从 `/api/inbound/supplier/submit` 提交预计到达时间和商品/SKU 明细；新建明细要求当前 SKU，数量为正整数。供应方只能查看和修改归属自己的单据，并需要 `inbound:create` 或 `inbound:view`。管理端通过 `/api/inbound/admin/verify` 使用核验码确认到货，需要 `inbound:verify`；列表与详情读取需要 `inbound:view`。

### 8.2 状态机

```text
                    管理端核验并入库
            ┌──────────────────────────> verified
            │                                │
pending ────┤                                └─ 高风险删除：反向扣回库存并软删除
            │
            └─ 供应方取消 ─────────────> cancelled
                         cancelled ─恢复─> pending
```

普通取消只适用于 `pending`；`verified` 不能走普通取消。供应方取消原因真实规则为去除首尾空白后 1–255 字，并非“2–200 字”。已核验删除要求供应方归属、展示单号、高风险口令和路由频控；成功后状态仍保留为已核验历史，但单据进入软删除。

### 8.3 核验事务

```text
管理端输入核验码
  → 认证、inbound:verify、CSRF、DTO 校验
  → 开启事务并锁操作者账号
  → 锁送货单，确认 pending 且未删除
  → 按商品/SKU 稳定顺序加锁
  → 校验 SKU 当前、启用、归属正确与数量上限
  → SKU.currentStock += qty
  → Product.currentStock += qty
  → 写 inbound_sys 库存流水
  → 送货单改为 verified，保存核验人/时间快照
  → 写审计并提交
```

单据、库存、流水和审计共用事务。任何明细无效或越界，整单回滚。已核验删除执行相反方向，但先检查扣回后 `currentStock-preOrderedStock` 仍非负；因此已经被 O2O 预占的到货数量不能被错误撤回。反向流水使用独立变动类型，便于区分业务入库与删除回滚。

## 9. 扫码库存单据、盘点与普通库存作业

### 9.1 通用库存单据

`POST /api/inventory/docs` 支持采购入库、退货入库、其他出库、报损出库和调整。每单 1–200 行，同一 SKU 不得重复；入/出库数量为正数，由单据类型决定记账方向，调整单允许有符号数量。选择“其他”原因时必须填写备注。

客户端可发送 `clientRequestId`。服务端对单据类型、原因、备注和归一化明细生成内容摘要，并进行事务外快速查询与事务内二次查询。冻结源码中的处理意图可由 `backend/src/services/inventory-doc.service.ts` 的下列片段直接复核：

```ts
const requestDigest = buildRequestDigest(docType, reasonCode, remark, items)

if (clientRequestId) {
  const existing = await manager.getRepository(InvStockDoc)
    .findOne({ where: { clientRequestId } })
  if (existing) return { replay: existing }
}
```

返回已有单据前仍会比较操作者与摘要；相同请求重放，相同键不同内容返回 409。新单据在同一事务中分配单号、保存主单、调用共享记账、保存明细和审计。作废锁定原单与 SKU，按原数量做反向流水；入库单作废相当于扣回，若可售库存不足则整单拒绝。退役 SKU 不允许作废，以免历史规格重新影响当前聚合。

### 9.2 盘点状态机

冻结代码中的准确状态是 `counting → reviewing → completed`，不存在 `submitted` 状态。

```text
                 提交盘点
counting ─────────────────────> reviewing ───全部差异已处理──> completed
   ▲                               │
   └────────── 退回重盘 ───────────┘

counting  ─取消─> cancelled
reviewing ─取消─> cancelled
```

盘点范围可为全库、分类、库位或指定 SKU，默认盲盘，最多 5000 个 SKU。创建时占用命名范围互斥键 `inv_stocktake.scope_mutex`，并检查目标 SKU 不属于其他未结束盘点，防止两个盘点同时解释同一差异。

首次计数时保存账面快照和实盘值；提交时可选择将未盘项目视为零。审核人对差异逐项选择调整、报损、重盘或忽略，其中报损只允许库存减少，重盘项必须退回 `counting`。只有所有差异均有决议才能完成。完成事务调用共享记账生成盘盈、盘亏或报损流水，随后把明细标记为已应用并写审计。

盲盘保密在接口层执行：没有 `stocktake:approve` 的计数人员无法从详情或明细获得账面数、差异和审核决议；计数接口也不会在响应中回传账面库存。计数需要 `stocktake:count`，查看需要 `stocktake:view`，审核、退回、完成和取消需要 `stocktake:approve`。

## 10. 普通出库订单

### 10.1 创建链路

管理端从开单页调用 `POST /api/orders/submit`，需要 `orders:create`。DTO 包含幂等键、部门/客户信息、明细和业务信息；服务端强制手工出库数量为正整数。

```text
路由校验与权限
  → 事务内锁操作者账号
  → 按幂等键查询已有订单
  → 解析部门，锁当前商品/SKU
  → 校验状态、数量和 available
  → 生成 UUID、展示号、业务号
  → 保存订单（inventoryMode=manual_applied）及明细快照
  → 共享记账扣减物理库存并写流水
  → 更新需要同步的商品默认价
  → 写审计并提交
```

数据库唯一键处理最后的并发竞态：若两个相同幂等请求同时越过快速查询，其中一个创建成功，另一个捕获唯一冲突后返回已有订单，不会再次扣库存。

### 10.2 删除、恢复和历史模式

`inventoryMode` 显式区分库存语义：

| 模式 | 含义 | 删除/恢复处理 |
|---|---|---|
| `manual_applied` | 普通出库已在创建时扣物理库存 | 软删除可选择释放；恢复时若上次已释放则重新扣减 |
| `o2o_preapplied` | O2O 核销事务已经完成物理扣减 | 正式出库不能再次扣库存，避免双扣 |
| `legacy_none` | 历史订单未纳入新记账机制 | 只按兼容规则处理，不伪造库存流水 |

删除事务锁订单并校验展示号/业务号、合并关系和当前状态；只有源订单自己的明细参与库存释放，合并产生的派生行不重复处理。恢复时根据最近一次删除/恢复流水判断是否需要重新扣减，库存不足则恢复整体回滚。`manual_applied` 不允许永久删除，以保留已入账凭证；`legacy_none` 仅在已经软删除、管理员高风险口令校验通过且不存在合并限制时才可能永久删除。

订单修订、合并、合规标志和内容编辑分别使用 `orders:update`、`orders:merge`、`orders:edit` 等权限，并保留修订记录和 `editVersion`，防止基于旧页面覆盖新内容。

## 11. 客户端鉴权、商城、购物车与结算

### 11.1 客户端鉴权

客户端提供验证码、能力查询、注册、登录、找回密码、`/me`、退出、改密、资料和联系方式验证等接口。Web 会话使用独立 HttpOnly Cookie，写请求使用独立 CSRF Cookie/请求头。登录后的每次关键业务写入还会在事务内锁定客户端账号并复核状态、生命周期和停用信息；因此“登录后被管理员停用”的账号不能继续用旧页面提交订单。

### 11.2 浏览与购物车

商城先请求店铺配置和商品列表，Store 用用户维度缓存。加入购物车时本地根据最近一次可售量和限购量提示上限，但该判断只用于交互。目录刷新若发现冲突，将冲突显示给用户，不暗改数量。结算页从勾选项创建不可变快照，提交时带新的 `clientRequestId`，并禁用重复点击；网络重试继续使用同一键。

### 11.3 结算调用顺序

```text
商城响应（缓存/ETag）
  → 加入按用户隔离的购物车
  → 结算页刷新服务端目录并标记冲突
  → 生成不可变选中快照和 clientRequestId
  → POST /api/o2o/mall/preorders
  → 服务端重新锁商品/SKU、重算价格/限购/库存
  → 成功后本地清理已购项并刷新目录/订单
```

客户端提交的价格、商品名、库存和用户身份都不是可信字段；价格与快照由服务端当前商品/SKU生成。商城缓存只能提升读取性能，不能降低结算一致性。

## 12. O2O 预订单、核销与退货

### 12.1 提交 DTO 与幂等

下单 DTO 的核心字段为：`clientRequestId`、`isSystemApplied`、`pickupContact`、可选 `pickupAt`、备注和 1–200 条明细。`clientRequestId` 必须是 16–64 位、字符集为字母数字及 `:_-`；数量为正整数。服务端对归一化后的系统申请标志、联系人、备注、可选取货时间，以及按商品/SKU 排序的明细计算 SHA-256 摘要。

实体唯一约束为 `(clientUserId, clientRequestId)`。相同用户、相同键、相同摘要返回原订单；相同键但不同摘要返回 409。冻结源码 `backend/src/services/o2o-preorder.service.ts` 中的真实冲突判断为：

```ts
if (!order.clientRequestHash || order.clientRequestHash !== clientRequestHash) {
  throw new BizError('该下单请求键已被其他内容使用，请刷新结算页后重试', 409)
}
```

MySQL 遇到可重试死锁或锁等待超时时，最多重放三次完整下单事务，而不是只重试失败 SQL；SQLite 交给单写协调器，不执行这套行锁重试。

### 12.2 下单事务与预占

```text
客户端提交
  → 快速幂等查询
  → 开启事务并锁客户端账号
  → 事务内再次查幂等键
  → 汇总该用户同 SKU 的 pending 数量
  → 按 ID 锁商品，解析候选 SKU，再按 ID 锁最终 SKU
  → 校验商品上架、SKU 当前且启用、限购和 available
  → 保存预订单及价格/名称/规格/图片/客户快照
  → Product.preOrderedStock += qty
  → SKU.preOrderedStock += qty
  → 写 preorder_hold 流水与通知
  → 提交后返回订单
```

下单只增加预占，不改变物理库存。商品和 SKU 两级都保存预占，是为了同时保护聚合查询和规格级扣减。通知记录与订单在事务内形成，避免业务失败却产生成功通知。

### 12.3 主状态机与取消

```text
                         核销：物理库存和预占同时扣减
              ┌──────────────────────────────────────> verified
              │                                           │
pending ──────┤                                           └─ 退货审核：物理库存回补
              │
              └─ 客户取消 / 管理取消 / 超时 ─────────> cancelled
                         仅释放预占，物理库存不变
```

取消统一进入事务内的 `cancelOrderInManager`。它先对 `{id, status: pending}` 执行条件更新，只有抢到状态迁移的一方继续锁明细、商品和 SKU 并释放预占；另一个并发取消、核销或超时任务看到状态已变化后停止。因此不会发生两次释放。

客户端只能取消自己的待处理订单；管理端取消需要 `orders:update`，原因规则为去除首尾空白后 2–200 字。这个规则与供应方送货单的 1–255 字不同，不能混用。超时释放复用同一取消逻辑并标记来源为 system。

### 12.4 超时扫描

后台任务读取超时配置后分批处理，单轮最多 5 批，并用进程内 in-flight 标志避免本实例重入。每个批次单独开启事务。MySQL 对待处理订单使用悲观写锁与 `skip_locked`，多个工作者不会阻塞着重复处理同一行；SQLite 通过单写队列执行。下单之外，改单、取消、核销和退货入口也会检查订单是否已超时，避免只依赖定时任务及时性。

### 12.5 核销与正式出库

管理端通过核验码查询，再调用 `/api/o2o/verify`，需要 `orders:create`。事务锁管理账号和预订单，执行超时检查，确认状态为 `pending` 且不存在待处理退货，然后锁商品/SKU。每条明细都必须满足物理库存和预占库存不少于核销数量。

核销同时执行：

```text
SKU.currentStock        -= qty
SKU.preOrderedStock     -= qty
Product.currentStock    -= qty
Product.preOrderedStock -= qty
```

随后写 `preorder_verify` 流水、把预订单改为 `verified`，并在同一事务创建 `BizOutboundOrder`。正式出库使用固定幂等来源 `o2o-preorder-verify:<预订单ID>`，`inventoryMode=o2o_preapplied`，保存来源单据和明细快照。普通出库服务看到该模式不会再次扣库存。任何一步失败，预订单状态、库存、流水和正式出库一起回滚。

### 12.6 改单与退货

客户改单和管理端现场调整都会锁订单、客户、商品和 SKU，并把原订单数量加回“有效可用量”后再校验新数量：

```text
effectiveAvailable = currentStock - preOrderedStock + originalOrderQty
```

这避免订单把自己的既有预占误判为他人占用。客户端改单次数受配置限制；管理端现场调整不消耗客户端修改次数。

退货为独立子状态机：

```text
return.pending ──审核通过──> return.verified
       └────────驳回───────> return.rejected
```

创建退货时保存源订单状态快照，并扣除其他待审核退货数量，防止累计超退。若源订单仍为 `pending`，审核通过表示减少订单明细并释放相应预占；若源订单已 `verified`，审核通过表示增加物理库存并写 `preorder_return_inbound` 流水。待处理退货会阻止核销。待处理订单的退货使全部数量归零时，主订单由系统取消；业务状态同时进入售后/售后完成，但它不替代 `pending/verified/cancelled` 主状态。

## 13. 客服反馈与 SSE

### 13.1 入口与对象

客户端可读取门户配置，在认证后创建/查看自己的会话、上传和下载自己的附件、发送消息、确认已解决、撤回、满意度评价，并通过 `/api/client-feedback/stream` 接收事件。客服端通过 `/api/customer-service` 查询会话、回复、指派、改变状态、维护结构化字段与内部备注，并读取在线状态/SSE；查看与回复分别需要 `customer_service:view` 和 `customer_service:reply`。

会话状态为：

```text
open → processing → resolved → closed
  └──────── 客户撤回/关闭 ─────────┘
```

消息发送者分 client、service、system；内部备注以 `internalOnly` 标识，绝不进入客户端事件受众。满意度只允许对 `resolved` 或 `closed` 会话提交。

### 13.2 写事务与事件发布

```text
客户端/客服提交动作
  → 身份、归属或客服权限检查
  → 事务内锁账号和会话
  → 写会话/消息/未读数/状态
  → 写审计与通知记录
  → 提交事务
  → 提交成功后发布进程内 SSE 事件
```

SSE 不在事务提交前发送，避免浏览器先看到随后回滚的消息。服务维护令牌哈希而非明文，限制每个所有者、会话和进程的连接数，对连接建立频控；慢消费者会被关闭。连接通过 keepalive 保活，并在空闲或事件发送时重新核验持久会话与权限，校验失败即关闭。

当前 SSE 总线是单进程内存实现。它适用于 onebox 单实例；多实例部署必须接入受信任的跨实例消息总线，这一能力在冻结基线中未实现，不能把单进程 SSE 描述成天然支持水平扩展。

附件只接受受限图片类型，执行大小/归属/配额校验和草稿清理，通过认证下载接口读取，不把上传目录配置成匿名静态目录。

## 14. 用户、权限、配置与审计治理

### 14.1 管理端身份与权限

管理端支持 admin、operator、supplier 三类角色，并在角色基础上使用细粒度权限，例如商品查看/管理、库存查看/操作/作废、盘点计数/审核、订单查看/创建/更新/删除、入库创建/查看/核验、客服查看/回复、配置更新等。路由中间件是最终判定点；角色只用于少数明确边界和默认能力，不能替代权限。

管理登录受验证码和频控保护。成功后写 HttpOnly 会话 Cookie 与可读 CSRF Cookie，响应不返回访问令牌。Cookie 写请求必须满足双提交 CSRF；兼容 Bearer 的请求不允许把令牌放在 URL query。

### 14.2 账号生命周期

用户创建、资料修改、状态切换、密码重置、停用、恢复和永久删除分别受权限与角色限制。关键业务事务通过账号业务守卫锁定操作者行并复核启用状态。MySQL 使用稳定 ID 行锁，SQLite 由单写协调器串行，从而使账号停用与新业务写入得到明确先后顺序。

永久删除类接口只在服务端校验配置中的高风险口令，并叠加管理员角色、权限、确认字段和频控；前端不保存、不本地比较，日志与审计也不写入口令明文。

### 14.3 系统配置

配置按键和值及分组持久化。查看和更新权限分离；配置测试动作可再使用独立权限。通知地址、Webhook 等外部目标作为不可信输入，必须限制协议、地址范围和敏感回显。读取配置时敏感项脱敏；业务服务只消费验证后的有效配置，并为超时释放等关键配置提供保守默认值。

### 14.4 审计查询

审计查询仅对管理员及具备审计权限的账号开放，支持按动作、操作者、目标和时间筛选。业务审计详情保存必要快照和前后变化，不复制密码、Cookie、Token、数据库密码或完整敏感 URL。

## 16. 一致性、幂等与失败处理矩阵

| 链路 | 事务内原子对象 | 幂等/并发手段 | 失败后的可见状态 |
|---|---|---|---|
| 普通出库创建 | 订单、明细、物理库存、流水、审计 | 幂等键唯一约束；账号/商品/SKU 锁 | 全部回滚；可用原键安全重试 |
| 库存单创建 | 主单、明细、物理库存、流水、审计 | 请求键 + 内容摘要；稳定 SKU 锁 | 同载荷重放，异载荷 409 |
| 入库核验 | 入库单状态、物理库存、流水、审计 | 单据/商品/SKU 锁 | 核验失败仍为 pending |
| O2O 下单 | 预订单、明细、预占、流水、通知 | 用户+请求键唯一；摘要；完整事务重试 | 同请求返回原单，不重复预占 |
| O2O 取消/超时 | 主状态、预占释放、流水、审计 | pending 条件更新只允许一个赢家 | 失败不改变状态，不部分释放 |
| O2O 核销 | 主状态、物理/预占、流水、正式出库、审计 | 订单行锁；固定正式出库幂等键 | 任一步失败全部维持 pending |
| 已核销退货 | 退货状态、物理回补、订单数量、流水 | 源单/退货/商品/SKU 锁；可退数量扣除待审 | 失败仍为 return.pending |
| 盘点完成 | 盘点状态/明细、物理库存、流水、审计 | 范围互斥；差异全决议；稳定锁序 | 未决项存在则不允许完成 |

客户端遇到网络超时不能擅自生成新请求键，应先按原键重试或查询结果。服务端 409 表示业务冲突，需要刷新事实后再操作；503 表示临时写入拥塞，可在保留原幂等键的前提下退避重试。任何重试都不能绕过权限或账号状态复核。

## 17. SQLite 到 MySQL 的迁移与救援边界

### 17.1 自动迁移阶段

迁移不是在线双写，而是受控停写、不可变快照、复制校验和计划重启流程。

```text
管理员发起迁移
  → 校验目标为空或由本任务拥有、字符集/权限满足
  → 停止超时工作者，进入只读并等待在途写排空
  → 冻结后复核源数据库
  → 创建不可变 SQLite 一致性快照和流式 JSON 备份
  → 独立进程建立 MySQL Schema
  → 按主键分批复制、保持自增游标
  → 校验 Schema、内容哈希、行数/自增元数据
  → 写 cutover marker 与运行时数据源覆盖
  → 进程以计划代码 75 退出，由 onebox 重启
  → 新进程在 MySQL 上对照快照再次验证
  → 成功后结束维护并清理任务锁/临时密钥
```

复制按元数据定义的表顺序和主键批次执行，避免一次把全部数据载入内存。安全续跑最多两次；超过上限不继续自动尝试。只有强校验通过才允许切换运行时数据源。MySQL 应用连接使用 `utf8mb4`、UTC、连接池并关闭 `multipleStatements`。

### 17.2 失败与回滚边界

在 MySQL 正式接收新写入前，失败流程可恢复原运行时覆盖、清理切换标记并继续使用 SQLite 快照；若清理不完整则保持只读，避免误写。MySQL 已正式承接写入后，旧 SQLite 不再同步，因此直接切回旧库会丢失新数据，冻结实现明确不把它当作普通一键回滚。

### 17.3 限制性救援服务

正常业务启动失败时，入口只输出稳定错误码，不泄露连接信息；满足恢复条件时启动受限救援应用。救援态仅保留 `/health`（返回 503/RESCUE）和 `/api/database-rescue`，不装配用户、订单、上传、审计和后台工作者。

救援调用必须来自可信 HTTPS 或本机回环，并携带存放在独立控制文件中的任务级 Bearer，叠加频控、幂等键、操作 ID 和 60 秒准备 nonce。接口不接受任意 SQL、Shell、文件路径或数据库连接参数。服务会校验源文件身份与摘要、任务/维护/锁/标记/覆盖的所有权，并持久化 `PREPARED → RESTART_READY → VERIFYING → FINALIZING → COMPLETED` 阶段。SQLite 重启恢复最多尝试两次，回滚时保持 `DB_SYNC=false`，明确告诉运维当前不是双向同步状态。

## 18. 部署、运行和可运维性

### 18.1 onebox

onebox 镜像包含前端静态资源、Nginx 与 Node.js 后端。启动脚本检查管理员初始口令存在且不是默认值，但不在日志中打印真实值。数据与上传使用独立持久卷；默认 SQLite，MySQL 通过可选 compose overlay 启动 MySQL 8.4、`utf8mb4` 和 UTC 时区。后端健康检查与容器重启策略识别计划退出码 75，区分迁移切换和异常崩溃。

### 18.2 健康与维护态

`/health` 提供进程和数据源可用性；迁移/恢复期间全局维护状态向 Web 壳层展示横幅，前端阻止普通写操作，后端写屏障仍是最终保障。运行时错误桥接到统一错误提示与遥测入口，页面级错误由 Suspense/错误边界隔离，避免一个懒加载页面使整个壳层空白。

### 18.3 运行监控重点

- SQLite 写队列长度、等待超时和 503 比例；
- MySQL 死锁/锁等待重试次数及最终失败；
- O2O 待处理订单年龄、超时释放批次和预占异常；
- 库存流水与实体前后值不一致告警；
- SSE 连接数、慢消费者关闭和会话复核失败；
- 迁移阶段、只读屏障、计划重启和救援尝试计数。

## 20. 已知边界与非实现项

1. 当前参赛能力是 Web 管理端和 Web 客户端；仓库中其他端的代码不纳入本文功能承诺。
2. SSE 为单进程内存分发，多实例跨进程消息总线尚未实现。
3. SQLite→MySQL 是停写切换，不是持续双写；MySQL 正式写入后不能无损直接回滚到旧 SQLite。
4. 购物车和目录缓存是交互优化，不是库存或价格权威来源；离线提交不会跳过服务端复核。
5. 历史 `legacy_none` 出库保留兼容语义，不通过补造流水把旧数据伪装成新记账模式。
6. 盘点状态以代码中的 `reviewing` 为准；任何材料中的 `submitted` 都不应继续用于比赛说明。
7. 供应方取消原因是 1–255 字；只有管理端 O2O 取消原因为 2–200 字。两条规则来自不同路由 DTO。

以上边界不是功能缺陷的掩饰，而是冻结基线的真实工程边界。比赛演示与答辩应围绕已经形成闭环的 Web 业务、库存一致性、权限审计和可恢复迁移展开，不把调研项、规划项或其他分支代码描述为已交付能力。
