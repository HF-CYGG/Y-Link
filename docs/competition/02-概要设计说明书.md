> **文档定位**：说明系统的模块、接口、数据协作和运行方式，服务于评审、部署与联调；字段级数据库定义、页面原型和函数实现细节由详细设计材料承担。
>
> **事实基线**：`origin/main` 的冻结提交 `b149f945ad4702bc56487955ac2e2a0b8e359e2a`。本文技术结论只取自该提交的源码、依赖清单和部署文件。
>
> **参赛范围**：管理端 Web、客户端 Web/H5、供应方 Web、后端 API、SQLite/MySQL 数据库模式及 Docker 部署。仓库保留的 `apps/mobile/` 不属于当前参赛系统能力。

## 1. 总体目标与设计原则

Y-Link 面向商品主数据、供应送货、入库、库存、普通出库、线上预订和反馈客服这一连续链路。它不是把若干页面简单拼接在一起，而是将会改变库存、状态或权限的数据操作收敛到服务端规则、事务与审计中：供应方提交送货单后由管理端核验入库；客户端下单后占用库存，核销后关联正式出库；盘点和退货通过流水留下原因；反馈会话的客户内容与客服内部信息严格分离。

| 原则 | 架构落实 | 价值 |
| --- | --- | --- |
| 业务真源在服务端 | 路由只处理 HTTP，service 处理状态机、库存、事务和审计 | 页面或客户端缓存不能篡改业务结论 |
| 先校验再写入 | schema、身份、权限、对象归属和库存均在服务端复核 | 阻止绕过前端后的非法写入 |
| 跨表一致性 | 入库、出库、预订单、核销、退货、盘点使用统一事务边界 | 不留下“单据有了、库存没变”的半成功状态 |
| 最小权限 | 权限点为主，角色为高危操作补充；服务层复核个人数据归属 | 减少横向越权与误操作 |
| 快照可追溯 | 单据保存商品、规格、价格、人员等业务时点快照 | 主数据变更不污染历史凭据 |
| 渐进部署 | onebox 默认 SQLite，MySQL 为受控可选模式 | 降低初装成本，并保留扩展路径 |
| 失败可定位 | 健康检查、库存流水、审计、维护状态与救援控制面 | 让业务、权限和环境问题可区分 |

## 2. 系统边界与角色

系统覆盖内部库存协同与面向用户的在线预订、反馈闭环；不包含第三方支付、物流调度和真实外部消息投递。验证码、短信、Webhook 等外部能力以受控配置和安全校验为边界，比赛环境不应写入或展示真实凭据。

```text
│ 管理端 Web            客户端 Web/H5                供应方 Web             │
│ 商品/库存/报表        商城/订单/反馈               送货/历史               │
│       └──────────────────── HTTPS / /api ───────────────────────┐        │
│                                                                  │        │
│ Vue 3 单页应用 ← Nginx 静态托管与反向代理 ← Express API          │        │

│                                  TypeORM / 事务协调 / 审计        │        │
│                                               │                  │        │
│                            SQLite（默认）或 MySQL（可选）          │        │
└─────────────────────────────────────────────────────────────────┴────────┘
```

| 角色 | 主要能力 | 后端约束 |
| --- | --- | --- |
| 管理员、操作员 | 商品、库存、订单、报表、用户、配置、审计、客服 | 管理会话、权限点、Cookie 写请求 CSRF；高危操作另加管理员角色 |

| 客服人员 | 回复、指派、状态、内部备注 | `customer_service:*` 权限；内部字段不向客户返回 |

## 3. 逻辑架构

系统按前端应用、HTTP 中间件、业务服务和数据访问分层。分层的目的不是制造额外目录，而是让每一层只回答一种问题：前端回答“怎么显示和交互”；路由回答“谁能以什么格式调用”；服务回答“动作是否允许、怎样改变状态”；实体和数据库回答“如何持久化并约束关系”。

```text
┌──────────────────────── 前端应用层 ───────────────────────────┐
│ Vue 页面 │ Vue Router │ Pinia │ 共享壳层 │ API 模块 │ 组合式函数 │
└──────────────────────────┬─────────────────────────────────────┘
                           │ Axios / JSON / Cookie 或 Bearer
┌──────────────────────────▼─────────────────────────────────────┐
│ Express 路由与中间件：schema │ 认证 │ CSRF │ 权限/角色 │ 限流     │
└──────────────────────────┬─────────────────────────────────────┘
                           │ 业务输入对象、身份上下文
┌──────────────────────────▼─────────────────────────────────────┐
│ Service：商品 │ 入库 │ 库存 │ 出库 │ O2O │ 客服 │ 通知 │ 审计    │
│ 规则校验 │ 状态机 │ 幂等 │ 事务 │ 快照 │ 实时事件                │
└──────────────────────────┬─────────────────────────────────────┘
                           │ EntityManager / Repository
┌──────────────────────────▼─────────────────────────────────────┐
│ TypeORM 实体、SQL 增量脚本、SQLite 单写协调或 MySQL 连接池        │
└────────────────────────────────────────────────────────────────┘
```

| 模块域 | 前端责任 | 后端业务真源 |
| --- | --- | --- |
| 平台与身份 | 登录、路由守卫、菜单、主题、错误呈现 | 管理/客户端会话、权限、验证码、审计 |
| 商品与 SKU | 商品中心、标签、规格、图片、商城展示 | 主数据、当前 SKU、价格与库存口径 |
| 供应与入库 | 送货、单据池、扫码核验 | 单号/核验码、状态、入库和流水 |
| 库存与出库 | 库存、盘点、扫码、普通出库、报表 | 可用量、库存单据/流水、导出 |
| O2O | 商城、购物车、结算、订单池、核销、退货 | 预占、幂等、释放、核销转出库 |
| 客服与治理 | 反馈、客服工作台、配置、用户、审计 | 会话、消息、附件、SSE、维护控制 |

## 4. 前端概要设计

### 4.1 技术与路由组织

前端在 `src/` 中以 Vue 3、TypeScript 和 Vite 组织。`main.ts` 创建应用后注册 Pinia 和 Router；Element Plus 组件与图标按实际使用接入，避免运行时整体注入。Axios 集中在 `src/api/http.ts`，业务 API 模块只描述请求、DTO 和响应转换，页面不散落 URL 或原始异常处理。

`src/router/routes.ts` 是路由真源。管理端菜单、工作台快捷入口、客户端底部导航和可访问性都从同一份 `meta` 派生。关键元信息包括 `title`、菜单分组、`requiredPermissions`、`allowedRoles`、`keepAlive`、`viewKey`、预热目标及客户端认证标识。路由守卫按需恢复相应会话，然后处理登录跳转、站内安全回跳和权限不足回退；前端门禁只优化体验，服务端仍是唯一授权裁决者。

### 4.2 共享壳层、Store 与稳定请求

管理端 `AppLayout.vue` 组合侧栏、顶栏、主内容区和异常兜底，并以 `Suspense + KeepAlive` 承接高频页面。不同入口可通过 `viewKey` 复用同一业务壳；没有明确缓存键时按完整路由区分，防止查询条件串状态。客户端 `ClientMainLayout.vue` 提供响应式主区、底部导航和切页过渡；订单详情、结算和会话等沉浸页可由路由元信息隐藏导航。

Pinia 将管理端身份、客户端身份、购物车、商城目录、订单缓存和主题拆分管理。管理端 Store 保存安全用户快照、权限和初始化状态，不将 token 当作业务状态。客户端退出或换号时清理用户关联缓存；购物车缓存仅用于恢复，目录刷新会更新库存、价格和可购状态，若发生冲突则要求用户显式处理，不能静默缩量。

高频筛选、分页和详情刷新通过 `useStableRequest` 处理竞态。新请求中止旧请求，并且只有最后一次请求可回写界面：

```ts
latestRequestId += 1
const requestId = latestRequestId
activeController?.abort()
const controller = new AbortController()
const result = await options.executor(controller.signal)
if (!controller.signal.aborted && requestId === latestRequestId) {
  await options.onSuccess(result)
}
```

页面只保留业务独有的字段映射和联动；分页、空态、错误态、工具栏、响应式抽屉、弹窗与权限动作由共享组件和组合式函数承担。这样既保留管理端的信息密度，也避免每个页面再实现一套滚动和错误处理逻辑。

### 4.3 UI 与响应式策略

管理端以 Element Plus 的表单、表格、树、分页、抽屉和确认组件为主，图表区域使用 ECharts/Vue ECharts。宽屏强调筛选、表格和批量操作；窄屏逐步收紧内容边距，长内容由统一壳层滚动，避免页面和弹层双重主滚动。客户端 Web/H5 强调单手操作和连续路径，商城、购物车、结算、订单和反馈使用清晰的返回关系；动效只提供轻量反馈，库存、权限和网络结果必须以清晰文本和状态标签表达。

## 5. 后端概要设计

### 5.1 启动、路由与中间件

后端在 `backend/src/` 中采用 Express + TypeScript。`index.ts` 是薄启动入口：先检查数据库启动状态，再装配业务运行时。数据库或运行时装配失败时，进程不以半可用状态提供普通 API，而进入独立救援控制面；公开健康检查只返回必要状态，不泄露连接、队列或凭据细节。

`app.ts` 依次装配 HTTP 安全头、匿名认证限流、上传资源策略、公开路由、受保护管理端路由和统一错误处理。管理端 `/api` 默认先经过 `requireAuth` 与 `requireAdminCsrf`，再进入商品、订单、库存、报表和系统治理模块；客户端认证、反馈和 O2O 各自保留必要公共接口，并在读写本人数据时加入客户端身份中间件。

下面的路由装配摘录体现了“认证和 CSRF 已在公共 `/api` 前缀收口后，业务路由再按领域拆分”的方式；它不是接口清单，详细参数仍由各路由 schema 定义：

```ts
app.use('/api/products', productRouter)
app.use('/api/orders', orderRouter)
app.use('/api/inventory', inventoryRouter)
app.use('/api/data-maintenance', dataMaintenanceRouter)
```

```text
请求
 ├─ 公共健康/匿名能力：限流 → 参数解析 → 业务路由
 └─ 管理业务 /api：认证 → Cookie 写请求 CSRF → JSON 限制
                     → 权限/角色 → schema → service → 统一 JSON 响应
                                                │
                                  BizError / Zod 错误 / 未知异常
                                                │
                                           最终错误处理中间件
```

### 5.2 Route–Service–Entity 职责

路由层负责取身份、挂中间件、校验输入、调用 service 和返回 HTTP。以 O2O 为例：商城目录可匿名访问，创建和查询本人预订单需 `requireClientAuth`；管理端核销需 `orders:create`，高危删除再叠加 `orders:delete` 与管理员角色。入库模块将供应方入口、管理端核验和单据池分开，避免仅凭同一权限点横向访问。

Service 是业务真源。`o2o-preorder.service.ts` 负责商城快照、预订单、取消、超时释放、核销、退货与库存日志；`inbound.service.ts` 处理送货单和核验入库；库存相关 service 处理单据、盘点与流水；`client-feedback.service.ts` 处理会话、消息、指派、内部备注和实时事件。服务接收明确的输入对象与身份上下文，不直接读取 `req`、`res`。

Entity 层以 TypeORM 映射表、字段、索引和关联，不承载跨表流程。`config/data-source.ts` 集中登记实体，使正常运行与迁移使用同一数据模型；`backend/sql/` 保存存量库演进的增量脚本与数据库级约束。

### 5.3 事务、审计与错误处理

库存、状态和多个聚合对象同时变化的操作使用 `runInTransaction` 或 TypeORM 事务；相关 Repository 共用同一 `EntityManager`。SQLite 使用受控单写协调降低锁竞争，MySQL 使用连接池，并仅对明确可重试的事务冲突做有限重试。项目禁止用多段裸 SQL 的 `BEGIN/COMMIT` 拼接事务，以免单连接环境中无法可靠识别事务所有者。

审计记录操作者、动作、目标、结果和必要摘要，禁止记录密码、Cookie、Token 或连接信息。Zod 参数错误会转换成稳定业务错误，最终中间件统一输出 JSON；前端将其转换成中文可理解提示，而不展示堆栈。

## 6. 关键业务流程

### 6.1 O2O：预订单、核销与退货

客户端显示的库存只是商城快照，提交时服务端仍在事务内复核商品、SKU、身份、状态和可用量。预订单以客户端用户与请求标识建立幂等边界，保存价格、规格、商品和提货等历史快照。创建时增加预占量；取消或超时释放预占；管理端核销生成关联正式出库记录，避免走普通出库链路再次扣减。退货按原订单状态确定回补口径。

```text
客户端结算
  → 复核商品/SKU/可用量/身份/请求幂等
  → 事务：preorder + items + 快照 + 库存日志
  → currentStock 不变，preOrderedStock 增加

pending ──取消或超时──→ cancelled：释放预占并记录原因
pending ──管理端核销─→ verified：完成库存处理并关联正式出库
verified ──退货申请/核验→ 退货状态及对应库存回补
```

### 6.2 供应送货与入库

供应方提交预计到货时间和至少一条明细后，服务端生成展示单号和核验码，单据先处于 `pending`。供应方只能操作本人单据；管理端按权限与角色查看单据池。库管扫码核验时，服务端事务内确认单据和相关商品/SKU 仍可入库，再写入库存结果及流水。撤销单据进入 `cancelled`；已核验单据的敏感删除另有高危门禁和审计。

```text
供应方提交 items[] → pending 单据 + 展示号/核验码
                       ├─ 撤销并填原因 → cancelled
                       └─ 管理端扫码 → 事务：入库 + 库存流水 → verified
```

### 6.3 盘点、库存与普通出库

商品与 SKU 均有物理库存和预占库存，服务端统一计算可用量。普通出库、入库、盘点和调整通过业务单据及 `InventoryLog` 记录来源，而不是让页面直接改余额。盘点单保存范围、明细和状态；完成时将账面与实盘差异转换为流水。普通出库以幂等键防重复，以版本约束处理修订，且始终校验 SKU 当前有效性、库存模式和业务状态。

### 6.4 客服会话与实时协同

客户端创建会话、发送消息、查询自己的进度和附件；客服工作台按权限查看、回复、接单/转派、改状态和维护内部备注。会话主表保存编号、客户快照、状态、优先级、负责人、最近消息和未读计数，消息/附件独立保存。服务端在消息、负责人、状态或内部备注变化后发布 SSE 事件，使两端更新相应视图；内部备注绝不进入客户端数据视图。

## 8. 安全与权限设计

管理端优先采用 HttpOnly Cookie 会话，并兼容 Bearer；客户端采用独立客户端会话 Cookie 或支持的 Bearer 方式。访问 token 不放入 URL query。管理端 Cookie 会话的写请求必须携带匹配的 CSRF 请求头，前端不能自行绕过此约束。

权限点决定日常业务能力，管理员角色用于数据库维护、批量删除等高危动作。菜单、路由和按钮可依据权限快照优化体验，但后端 `requirePermission`/`requireRole` 是最终门禁。客户端订单、反馈及供应方送货单在 service 层再次校验归属，不能仅信任路由参数。

上传资源按业务目录存储，静态响应带不可嗅探、资源级 CSP、引用策略和长期缓存头；历史路径在后端内部兼容改写。外发 URL、Webhook 和通知地址都应视作不可信输入，必须校验协议、域名和内网地址。Nginx 对页面、反向代理、认证入口、商城读缓存和上传资源采用不同的限流、缓存和安全头；公开商城读可短时缓存，真实下单永远回到事务复核库存。

## 9. 接口约定与异常处理

| 接口域 | 典型路径 | 输入关注点 | 返回/安全边界 |
| --- | --- | --- | --- |
| 身份 | `/api/auth/*`、`/api/client-auth/*` | 凭据、验证码、会话与 CSRF | 返回安全用户视图；认证结果不得缓存 |
| 商品库存 | `/api/products`、`/api/inventory` | 商品/SKU、分页、扫码、盘点 | 管理权限，服务端校验数值与当前有效性 |
| 供应入库 | `/api/inbound/*` | 送货明细、预计时间、核验码、撤销原因 | 供应方归属或管理权限；核验写入库存结果 |
| O2O | `/api/o2o/mall/*`、`/api/o2o/orders/*` | 请求标识、提货信息、SKU、数量 | 商城读可匿名；个人订单与管理核销身份分离 |
| 客服 | `/api/client-feedback/*`、`/api/customer-service/*` | 会话、消息、状态、负责人、内部备注 | 客户仅本人；客服查看与回复权限分离，支持 SSE |
| 治理 | `/api/system-configs`、`/api/audit-logs`、`/api/data-maintenance` | 配置、筛选、维护动作 | 细粒度权限，部分动作额外角色门禁 |

接口以 JSON 为主，服务端 schema 将不合格输入转换为受控错误。400 表示参数或业务前置条件不满足，401 表示未认证，403 表示无权限或 CSRF 不满足，404 可用于避免泄露不应见资源，409 表示库存、状态或版本竞争，429 表示敏感入口过频，5xx 表示未预期服务端故障。响应和日志不得包含堆栈、密码、Token、Cookie 或数据库连接信息。

## 10. 部署架构与运行时拓扑

比赛推荐 `Dockerfile.onebox` 与 `compose.onebox.yml`。onebox 在一个容器中运行 Nginx 与 Node：Nginx 对外托管 Vite 静态产物，并将 `/api`、`/health` 转发给容器内 Express；Node 不直接暴露给宿主机。SQLite 数据和上传目录使用持久化卷，入口脚本监测两个关键进程，任一异常退出即使容器退出并由编排策略重启。

```text
浏览器
  │ http(s)://host:port
  ▼
Docker compose：ylink 容器
  ├─ Nginx :80
  │   ├─ /、/client、管理路由 → Vite 静态文件 / SPA 回退
  │   ├─ /api、/health       → 127.0.0.1:3001 Express
  │   └─ /uploads            → 共享目录；未命中回落后端
  ├─ Express :3001（容器内部）
  ├─ /app/data    ← SQLite 持久化卷（默认）
  └─ /app/uploads ← 上传持久化卷

可选：同一内部网络的 MySQL 8.4 服务（默认不发布宿主机端口）
```

SQLite 是默认单机模式，启动时采用 WAL/PRAGMA 与有界写协调。MySQL 使用 `mysql2` 和连接池，适合更高并发或后续扩展。启动 MySQL 服务并不等于已迁移业务数据；SQLite 到 MySQL 必须经受控流程完成预检查、备份、复制、校验、切换和回退，不能用自动同步或直接改环境变量替代。

onebox 的入口脚本以两个受监控的前台关键进程组成最小运行拓扑。下面的摘录说明 Nginx 和后端共处一个容器，但由进程守护逻辑确保任一关键进程退出都不会留下貌似可用的残缺服务：

```sh
node /app/backend/dist/index.js &
BACKEND_PID=$!
nginx -g "daemon off;" &
NGINX_PID=$!
```

## 13. 性能、可维护性与取舍

| 场景 | 当前机制 | 原因 |
| --- | --- | --- |
| 首屏与页面跳转 | 路由懒加载、按高概率下一跳预热、UI 按需引入 | 避免加载尚未访问的业务页 |
| 高频筛选 | `AbortController` 与最新请求编号 | 防止慢响应覆盖最新交互结果 |
| 商城目录 | Nginx 短 TTL 微缓存；下单仍事务复核 | 降低公开读热点，不放宽库存真相 |
| 图片资源 | 哈希资源长期缓存、onebox 共享目录直出 | 减少重复下载和代理缓冲 |
| 列表与报表 | 服务端筛选、分页、导出与预览分离 | 防止浏览器持有全量业务记录 |
| SQLite 写入 | WAL/PRAGMA 与有界单写协调 | 降低单机模式的锁竞争和无限排队 |

系统刻意不建立“万能页面”或“万能服务”。共享层只解决重复 UI、请求和权限体验，库存、订单、入库和客服仍保留各自语义清晰的 service。SQLite 适合默认单机部署，但不是无限并发或多节点共享方案，因此保留 MySQL 与迁移治理。商城可以缓存匿名读，订单和会话不能按同样方式缓存；前端权限可改善体验，但绝不是安全边界。

## 14. 当前限制与演进边界

1. 本文只描述冻结基线已实现的 Web 能力；第三方支付、物流平台和真实外部消息发送不属于当前范围。
2. 双数据库模式不意味着可随时直接切库。迁移必须在目标环境重新完成预检查、校验、切换和回退验证。
3. 比赛文档、截图和演示不得包含账号密码、Cookie、Token、Webhook、数据库连接地址或其他私密值。
4. 具体字段、索引、SQL、请求体和函数实现属于数据库设计、接口材料和详细设计，不在本概要说明书展开。
5. 缓存、分页和写协调属于工程策略，不构成对任意硬件、网络和数据规模的固定性能承诺，实际部署仍应复测。
