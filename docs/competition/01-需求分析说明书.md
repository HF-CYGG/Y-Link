# Y-Link 文创出入库与 O2O 预订系统需求分析说明书

## 1. 文档说明

### 1.1 编制目的

Y-Link 面向文创、非遗、门店和活动销售场景，将商品主数据、供货入库、库存作业、普通出库、线上预订、线下核销和客户服务串成可追溯的业务链。本文说明当前版本要解决的问题、应提供的能力、约束规则和验收口径，为后续概要设计、数据库设计、测试文档及正式 DOCX 排版提供统一依据。

本文不是页面菜单清单，也不以“有某个页面”代替需求说明。核心需求按“角色/场景/问题 → 系统能力 → 业务规则 → 异常处理”的方式表达。

### 1.2 冻结基线与事实边界

本文的已实现能力仅以 Git 冻结提交 `b149f945ad4702bc56487955ac2e2a0b8e359e2a` 为事实来源。文中“系统支持”“当前实现”等表述均指该提交中的 Web 前端、Express 后端与数据库实体；不以当前工作分支、未提交文件或设想功能补充事实。

本期交付范围仅为管理端 Web、客户端 Web/H5、供应方入口、后端服务、SQLite/MySQL 数据库模式和容器部署；Mobile 不在本期成果和验收范围。

### 1.3 产品定位

本系统定位为“以库存真实性为核心的文创商品协同经营系统”。它既服务于后台人员和供应方的实物进出库，也服务于普通用户线上浏览、预订和到店取货。设计重点不是单纯记录订单，而是在商品规格、库存占用、价格快照、核销出库、退货回库、操作审计之间保持一致，使业务人员能够回答“库存为什么变化、订单现在处于什么阶段、由谁处理、是否已形成正式出库”的问题。

### 1.4 术语

| 术语 | 含义 |
| --- | --- |
| 商品 / SKU | 商品是对外展示和管理的主记录；SKU 是具体规格、编码、价格与库存的最小作业单元。 |
| 物理库存 | 已实际入库、尚未实际出库的 `currentStock`。 |
| 预占库存 | 已被待核销线上订单承诺、但尚未实际出库的 `preOrderedStock`。 |
| 可售库存 | 在当前 SKU 上按 `max(0, currentStock - preOrderedStock)` 计算的可继续预订数量。 |
| 预订单 | 用户线上提交、等待线下核销的订单，不等同于正式出库单。 |
| 核销 | 管理端依据核验信息确认取货或办理退货的动作；成功后才落实相应库存和正式单据结果。 |
| 普通出库 | 后台人员按业务需要直接开具的出库单，与 O2O 预订单核销形成的正式出库单区分处理。 |

## 2. 业务目标、范围与角色

### 2.1 业务目标

1. 把供应送货、库存入账、商品销售、线上预订与线下交付放在同一业务口径中，减少手工台账和重复录入。
2. 让每次库存改变都有来源单据、操作人和前后库存快照，支持日常核对、异常追查和运营报表。
3. 在高并发或重复点击下，优先保证“不超卖、不重复扣减、不把历史价格和规格改成当前值”。
4. 让普通用户完成登录、选购、下单、查询、撤回和反馈，同时将高风险操作留在受控的后台权限与审计体系内。

### 2.2 本期范围

| 范围 | 本期内容 |
| --- | --- |
| 商品与库存 | 商品、标签、SKU、线上展示状态、条码、分类/库位、库存流水、库存单据和盘点。 |
| 供货与入库 | 供应方送货单、本人历史查询与撤销；后台扫码/核验入库及库存回写。 |
| 出库与报表 | 普通出库开单、单据治理、库存及销售报表、运营看板与导出。 |
| O2O 履约 | 商品大厅、购物车、预订单、库存预占、取消/超时释放、线下核销、正式出库、退货申请与退货核销。 |
| 用户与治理 | 管理端/客户端认证、RBAC、系统配置、审计、账号生命周期和客服工作台。 |
| 部署与数据 | SQLite 默认部署、MySQL 目标模式、受控迁移、容器化交付与验证脚本。 |

### 2.3 非目标与边界

1. 本期不是 ERP、财务结算或物流调度系统，不承诺对接第三方支付、快递或外部财务系统。
2. 外部验证码、通知和 Webhook 属于配置与安全边界；其可用性依赖部署方合规配置，不能把第三方通道能力写成系统无条件保证。
3. 商品目录缓存和前端本地购物车用于改善体验，不是库存或订单的权威数据源；下单时必须由后端重算。
4. 线上预订单在 `pending` 阶段仅占用库存，不能当作已完成实际出库；正式出库以核销结果为准。

### 2.4 角色与职责

| 角色 | 典型场景 | 系统能力 | 不可绕过的约束 |
| --- | --- | --- | --- |
| 普通用户 | 浏览、加购、预订、查询、撤回、申请退货、反馈 | 客户端商品大厅、购物车、订单和反馈会话 | 仅能操作本人订单/会话；下单前后端均按 SKU、库存和状态复核。 |
| 管理员 | 账号、权限、配置、删除治理、审计与运营决策 | 全局配置、用户治理、报表、审计、高风险操作确认 | 管理员身份不替代权限校验；永久删除等操作还需要服务端密码和业务复核。 |
| 操作员 | 商品维护、入库核验、出库、订单处理、客服协作 | 经授权的库存、订单、入库、报表和客服动作 | 只能使用授予的权限点；供应方身份不能借权限点完成后台入库。 |
| 供应方 | 提交送货单、更新或撤销本人未核验单据、查看历史 | 供应方送货和历史单据入口 | 服务端按 `supplierId` 二次收口，不能通过参数查看或修改他人单据。 |
| 客服人员 | 接单、回复、转派、更新会话状态、记录内部备注 | 客服工作台与实时会话 | 客户不可查看内部备注；负责人必须是可分配的客服用户。 |

| 编号 | 实际试用反馈 | 转化后的需求 | 冻结基线状态 | 状态判断依据与剩余边界 |
| --- | --- | --- | --- | --- |

## 4. 核心业务闭环

### 4.1 端到端流程

```text
供应方提交送货单
        │
        ▼
后台核验入库 ─────────────► 物理库存 currentStock 增加
        │
        ▼
商品/SKU 上架、标签与价格维护
        │
        ├──────────► 后台普通出库：扣减物理库存并写出库/流水
        │
        ▼
普通用户浏览 ─► 购物车 ─► 提交预订单
                                  │
                                  ▼
                     预占 preOrderedStock 增加，订单为 pending
                      ┌───────────┼────────────┐
                      ▼           ▼            ▼
                 客户撤回     超时自动取消     到店核销
                      │           │            │
                      ▼           ▼            ▼
                  释放预占     释放预占   扣减物理库存、释放预占
                                                │
                                                ▼
                                       生成关联正式出库单（verified）
                                                │
                                                ▼
                                   用户申请退货 ─► 后台核销退货并回库
```

### 4.2 商品、SKU 与标签

**角色/场景/问题：** 文创商品存在颜色、尺寸、套装等规格差异。若只在商品层维护库存和价格，用户下单、条码扫描和历史查询都会失真。

**系统能力：** 管理端维护商品基本信息、标签、SKU 规格组、默认价格、线上状态、图片和详情；SKU 维护规格文本、编码、库存、预占库存以及线上可售状态。商城仅展示符合线上展示条件的商品和当前可用规格。

**业务规则：** 当前且启用的 SKU 才能成为新订单、普通出库和库存作业的有效规格；多规格商品应显式选定 SKU。商品级库存用于汇总展示，SKU 是库存作业与 O2O 校验的最小单位。商品价格、折扣与规格可以后续维护，但已生成订单使用下单时的快照，避免历史金额被实时商品改动污染。标签用于商品组织、筛选和运营分析，报表与看板使用服务端统一口径。

**异常处理：** 商品或 SKU 被下架、规格不属于商品、库存不足、SKU 已退役等情况应拒绝写入，不以自动替换成其他 SKU 的方式继续提交。

### 4.3 供货送货与入库

**角色/场景/问题：** 供应方负责送货，库管负责确认实际到货。如果“提交送货单”和“库存增加”混在一起，容易把未到货数量提前当成现货。

**系统能力：** 供应方可以提交送货单、查询本人历史、在允许状态下修改或撤销；后台可以按核验信息查看详情并完成入库。入库后，库存流水和单据状态共同反映实物已入账。

**业务规则：** 送货单主状态为 `pending`（待入库）、`verified`（已核销入库）、`cancelled`（已取消），另以软删除标记处理可见性治理。每张送货单具有唯一展示单号和核验码；核验动作仅允许后台 `admin/operator` 执行。供应方只能处理归属自己的未核验单据。后台核验在事务中回写商品/SKU 的物理库存并记录入库来源，不能只把状态改为已核验。

**异常处理：** 重复核验、越权访问、已核验后修改、SKU 缺失/退役、冲销后会低于预占库存等场景应被拒绝并留存必要审计信息。

### 4.4 普通出库、库存流水与盘点

**角色/场景/问题：** 门店存在非线上订单的领用、销售、报损、调整和盘点。仅修改库存数字无法还原原因，也会与预订单履约相互干扰。

**系统能力：** 管理端提供普通出库开单、库存单据、库存流水、当前库存、条码扫描和盘点能力。普通出库与 O2O 核销使用不同库存模式，但共同遵循可用库存校验和流水可追溯原则。

**业务规则：** 新建普通出库以 `manual_applied` 模式在同一事务内写主单、明细、库存扣减和库存流水；相同幂等键重放不能重复扣减。历史不追溯库存的单据保持 `legacy_none`；由 O2O 核销生成的正式出库为 `o2o_preapplied`，其库存已由预订单核销链路处理，通用内容编辑不能再次扣库。库存盘点以账面快照和实盘数计算差异，差异处理产生明确的库存流水；盘亏同样受可售库存约束。

**异常处理：** 可售库存不足、SKU 无效、并发版本过期、幂等键对应内容不一致、已删除或锁定单据再次编辑时，应整体回滚本次写入而非形成半张单或半段流水。

### 4.5 O2O 预订、取消、核销与退货

#### 4.5.1 用户下单与库存预占

**角色/场景/问题：** 多名用户可能同时购买同一规格。仅根据前端展示库存提交，会导致超卖或“看似成功但只成交部分数量”。

**系统能力：** 客户端提供商品浏览、购物车、结算和订单详情；后端在事务中锁定待下单的商品/SKU，复核价格、状态、限购和库存，创建预订单与明细，同时把预占数量写入商品/SKU及库存流水。

**业务规则：**

- O2O 主订单状态固定为 `pending`、`verified`、`cancelled`。备货、待取货、发货等业务进度属于附加业务状态/状态报告，不能替代主状态。
- 可售库存的权威公式是 `availableStock = max(0, currentStock - preOrderedStock)`；提交时按 SKU 使用未截断的差值再次判断是否满足本次数量。
- 成功创建 `pending` 订单时，仅增加 `preOrderedStock`，不减少 `currentStock`，同时写入预占库存流水。
- 下单请求键由客户端携带，格式受后端校验。相同用户、相同请求键且载荷一致时返回既有订单；相同请求键却提交不同商品、数量或关键参数时返回冲突。
- 每个商品可配置限购规则。规则启用时，后端把用户现有待核销数量与本次请求数量合并校验，不能只检查购物车单行数量。

**异常处理：** 未登录、商品/规格下架、SKU 归属错误、库存不足、超过限购、请求键格式错误或请求键被不同内容复用时，订单、预占库存和流水应一并不落库。

#### 4.5.2 取消与超时释放

**角色/场景/问题：** 未取货订单长期占用库存会阻塞销售；取消动作若可重复执行，会造成重复释放。

**系统能力：** 客户端可撤回本人待核销订单；系统可识别超时订单并自动取消；管理端可人工取消订单。三种路径均由服务层在事务中处理库存释放和审计。

**业务规则：**

- 取消操作先以 `status = pending` 为条件更新为 `cancelled`，只有成功获得状态转换的一方能释放预占库存，避免并发撤回、超时回收和核销发生重复释放。
- 客户撤回来源为 `client`、原因标记为 `manual`；系统超时取消来源为 `system`、原因标记为 `timeout`；管理端人工取消来源为 `admin`、原因同为 `manual`，并保存人工说明。
- 取消或超时只减少 `preOrderedStock`，不改变 `currentStock`，因为待核销阶段没有发生实际出库。
- 管理端人工取消的说明在路由和服务层都校验为去空白后 2–200 个字符，并会展示给客户。客户端主动撤回接口不接收该说明；不得把此长度要求错误施加到用户撤回或系统超时。

**异常处理：** 订单已核销、已取消、已超时或状态被其他请求抢先改变时，返回明确冲突结果；库存释放、库存日志、状态和审计必须同事务成功或失败。

#### 4.5.3 到店核销与正式出库

**角色/场景/问题：** 预订并不等于取货。若在下单时直接扣减现货，用户撤回或过期会难以复原；若核销可重复生成出库单，则会造成重复出库。

**系统能力：** 管理端核销待取货订单后，将对应数量从物理库存扣减、释放预占，并生成与该预订单关联的正式出库单。

**业务规则：** 核销后预订单转为 `verified`；库存变化同时反映 `currentStock` 减少与 `preOrderedStock` 减少，并写入核销库存流水。正式出库单使用预订单标识构造关联幂等键，重复核销或重试时复用已有正式单据。正式单保存结构化来源单据快照，人工备注与来源追溯分离；订单明细继续使用下单时的商品、价格和规格快照。

**异常处理：** 核销时发现订单超时，应先走超时取消与释放逻辑并阻止核销；订单不在 `pending`、核验信息错误、关联正式单数据不一致时不得继续扣减库存。

#### 4.5.4 退货申请与退货回库

**角色/场景/问题：** 用户已取货后可能需要申请退货。若退货直接修改原预订单，会丢失申请、审批和回库过程。

**系统能力：** 用户针对本人原预订单提交退货申请并选择明细数量、说明；管理端查看、处理、拒绝或核销退货。退货申请是独立对象，不等同于预订单状态。

**业务规则：** 退货数量不得超过原订单对应明细的可退数量；历史规格以订单快照展示。退货核销根据原订单在退货时的来源状态决定库存回到预占还是现货，避免把尚未完成的预订与已完成出库混为同一库存状态。退货申请、处理意见、处理人和处理时间可追溯。

**异常处理：** 非本人访问、重复或超量申请、订单不满足退货条件、并发处理导致剩余数量变化时，必须拒绝并保持原库存与申请状态一致。

### 4.6 订单合并与历史兼容

**角色/场景/问题：** 后台可能需要在同一业务日期内将多张符合条件的正式出库单汇总处理，但不能因此重扣库存或让来源单据消失。

**系统能力：** 管理端提供预览后提交的订单合并能力，目标原订单保留为父根，来源原订单形成一层来源关系。

**业务规则：** 正式出库单合并状态为 `active` 或 `merged`；父根保持 `active`，来源原单变为 `merged`，不新建订单号、不重复扣库存。合并复制的来源明细保存原单与原明细出处；合并操作保存幂等键、请求摘要和结果快照。合并受订单类型、统计日期、状态、库存模式、客户/部门和 O2O 约束共同限制。

**异常处理：** 版本冲突、跨统计日、来源单已被合并、存在不满足 O2O 约束的退货或打印证据时，预览/提交明确失败，且不改变库存与订单关系。

### 4.7 运营报表与工作台

**角色/场景/问题：** 管理者需要了解库存、销售、产品、客户和出库趋势；若用前端全量数据临时计算，不同页面会出现不同结果。

**系统能力：** 管理端提供工作台统计、趋势和排行榜，以及库存、标签销售、散客、金蝶和出库流水等报表，支持分页预览与 Excel 导出。

**业务规则：** 报表字段、筛选、分页和导出由后端统一定义。库存报表按当前有效 SKU 汇总物理库存和预占库存，在没有当前 SKU 的兼容场景下才按商品主记录回退。历史出库、商品名、SKU 规格和价格使用单据快照；工作台与报表排除不应参与统计的删除/合并来源记录。

**异常处理：** 大量数据导出应以服务端批处理/流式方式完成；筛选条件非法、页面超过服务端可用页码或字段不在白名单时，返回收敛后的分页/校验结果而不是生成不可解释的报表。

### 4.8 反馈客服与服务闭环

**角色/场景/问题：** 用户遇到订单、商品或服务问题时，单纯留下文本无法形成处理责任和闭环。

**系统能力：** 客户端提供反馈会话的创建、消息追加、详情查看、确认解决、撤回和满意度反馈；客服工作台提供查询、回复、接单/转派、状态更新、结构化问题字段和内部备注，并通过 SSE 推送会话变化。

**业务规则：** 会话以唯一编号、状态、优先级、负责人、主题、问题类型、标签和未读状态组织；客服接单、转派和状态变化可形成系统消息。服务层校验会话归属，普通用户只能读取和操作自己的会话。客服查看与回复分别要求相应权限，内部备注不返回客户端；实时事件覆盖消息、负责人、字段、状态和内部备注变更。

**异常处理：** 无权访问、负责人不可分配、状态转换不允许、SSE 中断或附件不合规时，接口给出可恢复的错误，客户端不以本地假状态替代服务端结果。

## 5. 关键业务规则与数据一致性

### 5.1 库存口径与不变量

| 编号 | 规则 | 验收要点 |
| --- | --- | --- |
| BR-01 | 物理库存为 `currentStock`，预占库存为 `preOrderedStock`，可售库存为 `max(0, currentStock - preOrderedStock)`。 | 商城展示、购物车预检与服务端提交校验使用同一公式；最终以下单事务内 SKU 校验为准。 |
| BR-02 | 创建预订单只增加预占；取消/超时只释放预占；核销同时减少物理库存与预占。 | 任一动作后库存日志中的前后快照、商品汇总和 SKU 值可相互核对。 |
| BR-03 | 入库增加物理库存，不改变预占；普通出库只在对应库存模式下扣减。 | 入库、普通出库和 O2O 核销不得借用彼此的库存语义。 |
| BR-04 | 不能出现负的可售库存；盘亏、冲销、删除回补等反向动作先校验未核销预占。 | 预占量大于物理库存时，拒绝会进一步恶化差额的写操作。 |
| BR-05 | 库存流水是追溯依据，而不是可选日志。 | 每次实际库存/预占改变带有来源类型、关联单据、操作者和变更前后值。 |

### 5.2 事务、并发与幂等

1. 订单、库存、入库、退货、删除治理等多实体写操作应在同一数据库事务内完成；任一校验或写入失败时整体回滚。
2. 下单、普通出库、订单合并等重复提交风险高的动作使用幂等键与请求摘要。重复请求可安全返回已有结果，内容不一致的重复键必须报冲突。
3. 影响库存的服务层应按稳定顺序锁定相关商品和 SKU；在 MySQL 模式下使用适当的悲观锁或事务重试策略，在 SQLite 模式下遵循应用的单写协调约束。
4. 普通出库内容修改使用 `editVersion` 做乐观并发控制，避免后保存的页面将前一位操作者的新数据覆盖掉。
5. 读取目录、购物车缓存和页面预检都可能过期。它们只能改善交互，不能代替提交事务中的状态、库存、SKU 归属和限购复核。

### 5.3 取消、删除和可见性治理

1. 取消、软删除、恢复和永久删除是不同动作。软删除通常影响列表可见性；永久删除是高风险治理，不等同于普通取消。
2. 高风险永久删除除权限外还需要管理员角色、服务端永久删除密码、必要的单号/账号二次确认、业务关联复核和审计。
3. 承载库存影响的普通出库单不能因永久删除而失去库存依据；O2O 关联单据、合并关系、已入库冲销凭证也要保留必要的追溯边界。
4. 客户端查询以本人归属为硬约束。即使订单已合并或关联正式出库，也不能通过当前单号、来源单号或参数枚举泄露其他客户数据。

### 5.4 防恶意注册与下单的实际边界

**已落地的注册防护：** 客户端注册入口校验账号、密码和身份字段；个人注册要求完成联系方式验证码核验；验证码发送前有图形验证码校验。服务端对注册、图形验证码和验证码发送按风险来源/IP 回退桶以及账号或目标维度实施频控，并记录相应安全审计；注册还受账号唯一性、联系方式唯一性和教师身份校验约束。冻结基线中注册频控的当前配置分别包含来源 30 分钟 40 次、IP 回退 30 分钟 300 次、账号 24 小时 10 次；这些数值属于实现配置，后续应通过安全评审而非前端写死。

**已落地的下单防护：** 下单必须经过客户端认证；后端锁定商品/SKU，在事务中校验可售量和限购，使用请求键避免重复创建，并在状态竞争时拒绝错误转移。

**明确边界：** 在该冻结基线中，没有证据表明 O2O 下单路由已配置一个独立的“按来源/IP 的下单频控阈值”。因此本文不把“防止恶意下单”写成已由专门订单限流完全解决；当前主要防线是认证、事务库存校验、限购和幂等。若业务需要抵抗低频、多账号或自动化占库存，应另行完成风险评估后设计订单级频控、设备/行为识别与运营处置，而不能在本期文档中虚报为既有能力。

## 6. 安全、体验、可维护性与兼容性

### 6.1 认证与 RBAC

- 管理端与客户端会话分离。两端均优先支持安全 Cookie 会话并兼容 Bearer；管理端不接受 URL query 中传递的访问令牌。
- Cookie 会话下的非安全方法必须通过双提交 CSRF 校验；Bearer 兼容路径不应被错误降级为 Cookie 回退认证。
- 管理端以权限点控制业务能力，以角色控制管理员专属边界；前端隐藏按钮只改善体验，后端路由和服务层才是最终授权点。
- 权限拒绝、角色不匹配与 CSRF 失败写入安全审计。供应方、客户端用户和客服会话的对象归属还需要服务层二次验证。

### 6.2 高风险治理与审计

- 审计覆盖认证、权限拦截、订单与出库、入库与供应、商品与库存、客服消息、用户权限、系统配置、数据维护等重要动作。
- 审计详情、日志和错误提示不得记录密码、Token、Cookie、永久删除密码或外部通道密钥。
- 外部 URL、Webhook、上传资源和数据库救援/迁移入口均是安全边界，必须使用协议、网络地址、权限和来源约束，不能按普通文本输入处理。
- 账号注销、恢复和永久删除要区分状态变更与物理清理；历史订单、客服、通知等关键引用存在时不能静默解除关联或删除证据。

### 6.3 可用性与性能

- 管理端和客户端以响应式 Web 方式提供服务。高频刷新、长列表和自动同步区域应以轻量交互为主，并支持减少动态效果的用户偏好。
- 购物车输入、目录刷新和请求竞态避免旧请求覆盖新状态；本地存储失败时，可在当前内存会话继续操作，但刷新后可能无法恢复缓存，且不得放松后端校验。
- 报表和订单池采用服务端分页、筛选和导出，避免浏览器一次加载无界数据。
- 性能验证覆盖前端构建预算、核心页面路径和服务端启动/接口相关指标；性能优化不得改变库存、订单和权限语义。

### 6.4 部署、迁移和运维兼容

- 系统默认可运行在 SQLite，适合单实例、轻量部署；多人高频并发写入或持续增长场景应使用 MySQL。
- 容器化部署需持久化数据库与上传目录，前端、后端和反向代理可采用 onebox 或双容器模式。
- SQLite 到 MySQL 的迁移是受控流程：冻结业务写入、复制并校验数据、写入运行时覆盖、计划重启并验证健康状态。迁移不是普通页面点击行为，必须在隔离环境演练、备份和回滚预案齐备后执行。
- 历史数据兼容以可空 SKU、订单快照、历史库存模式和结构化来源字段为原则；新规则不应强迫改写旧订单的价格、名称和规格。

## 8. 验收口径与异常场景

### 8.1 核心验收场景

| 场景 | 验收口径 |
| --- | --- |
| SKU 预订竞争 | 两个用户同时争抢最后可售库存时，最多一个请求成功；失败请求不创建订单、不增加预占、不写半段流水。 |
| 重复提交 | 相同用户以相同请求键和相同内容重试，返回同一预订单；同一请求键配不同内容时明确冲突。 |
| 取消竞态 | 客户撤回、定时超时和管理端取消并发时，仅实际完成状态转换的一方释放一次预占库存。 |
| 核销闭环 | 待核销订单核销后状态为 `verified`，物理库存和预占库存同步变化，并形成一个关联正式出库单。 |
| 退货闭环 | 退货数量不能超过可退量；处理后库存回流位置与原订单状态匹配，申请和处理记录可查询。 |
| 入库边界 | 供应方不能核验入库或读取他人单据；后台核验后库存真实增加并留下流水。 |
| 普通出库边界 | 库存不足、SKU 无效、版本冲突或幂等键冲突时整笔普通出库不落库。 |
| 权限边界 | 没有权限的后台账号和跨账号客户端请求均被拒绝；拒绝动作具有安全审计。 |
| 高风险删除 | 未满足权限、管理员身份、服务端密码、二次确认或关联复核中的任一条件时，永久删除被拒绝。 |
| 反馈隐私 | 客户只能访问本人会话，客服内部备注不会出现在客户端详情。 |
