## 版本递增规则

- 自本次更新起，应用展示版本采用 `主版本.次版本.功能号.修复号`，例如 `1.5.0.1`；版本真值继续维护在 `APP_META.version`。
- 前两段由项目负责人决定，日常更新不自动升级 `1.5`。
- 新功能或功能增强：第三段递增，第四段归零，例如 `1.5.0.1` -> `1.5.1.0`。
- 仅包含 bug 修复：第四段递增，例如 `1.5.0.1` -> `1.5.0.2`；同批包含多个修复时只递增一次。
- 同批同时包含功能与修复时，按功能更新递增；仅文档、测试或不改变应用行为的工程调整不单独递增。
- 旧版本 `1.5.0` 视为四段格式的 `1.5.0.0`。四段格式用于应用展示，不写入要求三段 SemVer 的 npm 包版本字段。

## 阶段总结

- `v1.2.x`：从应用元数据、客户端基础体验起步，快速搭建客服反馈闭环，并补齐供货方改单与扫码入库辅助能力。
- `v1.3.x`：重点转向认证安全、上传路径兼容、性能治理、通知中心与客户端会话管理，逐步形成可上线的生产化能力。
- `v1.4.x`：进入业务扩展高峰期，完成客户端账号体系、教职工目录、系统配置、报表中心、O2O 折扣与 SKU 规格链路的大量迭代。
- `v1.5.0`：开始强调交付体验与视觉品质，补强 onebox 上传验证，并升级商城视觉与 README 预览展示。
