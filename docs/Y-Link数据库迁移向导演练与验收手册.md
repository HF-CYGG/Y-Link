# Y-Link 数据库迁移向导演练与验收手册

> **文档说明**：本文用于指导运维、实施与验收人员围绕“数据库迁移向导”完成正式迁移前演练与正式切换后验收。
> **适用范围**：Y-Link 从 `SQLite` 平滑迁移到 `MySQL` 的场景，覆盖成功、失败、重启、切换前取消/启动失败恢复四类关键过程。
> **维护口径**：若迁移向导页面字段、任务状态、切换机制或回退策略发生变化，必须先更新本文后再执行新的演练与验收。
> **推荐原则**：正式环境优先使用管理端 `系统管理 -> 数据库迁移助手` 完成预检、迁移和切换，不建议绕过向导手工拼接流程；MySQL 接收新写入后禁止直接回到旧 SQLite。

---

## 1. 演练目标

本手册关注四个必须被覆盖的场景：

1. **成功场景**：确认向导能够完成预检、迁移、切换，并通过核心业务验收。
2. **失败场景**：确认向导能识别阻断问题、保留失败信息，且不会把系统误切到异常库。
3. **重启场景**：确认“写入运行时覆盖配置”后，必须通过后端重启才能真正切换数据库。
4. **恢复场景**：确认切换前可以安全取消，或 MySQL 启动验收失败时由自动迁移状态机恢复 `SQLite`；确认切换成功并产生新写入后，直接回退会被阻断。

---

## 2. 角色分工

- **运维负责人**：准备数据库、执行备份、安排窗口、执行服务重启。
- **业务验收人**：负责登录、商品、订单、核销、入库等关键链路验收。
- **技术支持**：观察迁移任务状态、定位失败原因、确认回退可执行性。

---

## 3. 演练前准备

### 3.1 环境准备

- 准备一套可登录的管理端环境，确保可访问 `系统管理 -> 数据库迁移助手`。
- 准备一个带测试数据的 `SQLite` 源库，至少包含用户、商品、订单、库存等关键业务数据。
- 准备一个独立的 `MySQL` 目标库，建议为空库，避免与其他系统共用。
- 准备具备 `system_configs:view` 与 `system_configs:update` 权限的管理端账号。
- 在 Onebox 的 `.env` 中预先确认 `DB_POOL_SIZE`、`DB_CONNECT_TIMEOUT_MS`、`DB_ACQUIRE_TIMEOUT_MS`、
  `DB_IDLE_TIMEOUT_MS`、`DB_QUEUE_LIMIT` 和 `DB_MAX_QUERY_MS`；
  迁移任务只记录目标库连接信息，切换后的连接池参数仍来自容器环境变量。

### 3.2 备份准备

- 在宿主机侧备份当前 `SQLite` 文件，记录备份路径、备份时间、执行人。
- 确认目标 `MySQL` 已创建数据库、账号和最小必要权限。
- 确认运维窗口内允许执行一次后端重启。

### 3.3 验收基线

正式演练前，先记录以下基线数据，便于迁移后比对：

- 管理端账号数量。
- 客户端账号数量。
- 商品总数与至少 3 个重点商品库存。
- 最近 10 条订单编号与状态。
- 最近 5 条入库或核销记录。

建议把以上基线记录保存到变更单、验收单或项目运维记录中。

---

## 4. 通用验收项

无论执行哪一种场景，均建议在操作前后检查以下项目：

- 管理端登录是否正常。
- 客户端登录与商品大厅加载是否正常。
- 商品列表、订单列表、入库管理是否可打开。
- 新建一张测试订单是否成功。
- 核销或入库动作是否可执行。
- 后端健康检查是否可访问。
- `/health` 中数据库引擎为 `mysql`；后端日志没有持续出现连接获取超时、连接队列拒绝，慢查询阈值符合本次容量基线。
- 数据库迁移助手页面中的“当前运行状态”是否与实际预期一致。

---

## 5. 场景一：成功场景

### 5.1 目标

验证数据库迁移向导可以完成：

- 预检通过。
- 迁移任务成功执行。
- 写入 `MySQL` 运行时覆盖配置。
- 后端重启后正式切换到 `MySQL`。
- 核心业务链路验收通过。

### 5.2 操作步骤

1. 使用管理员账号进入 `系统管理 -> 数据库迁移助手`。
2. 填写目标 `MySQL` 连接信息。
3. 点击 `执行预检`，确认页面未出现阻断错误。
4. 保持 `初始化目标表结构`、`执行前创建 SQLite 物理备份` 开启。
5. 点击 `创建迁移任务`，在任务列表中找到新任务。
6. 点击该任务的 `执行`，等待任务状态变为 `已成功`。
7. 点击该任务的 `切换`，填写切换原因并确认。
8. 按运维流程重启后端服务。
9. 重启完成后返回数据库迁移助手，确认当前模式为 `mysql`。
10. 按“通用验收项”执行业务验收。

### 5.3 预期结果

- 预检结果显示“允许继续”。
- 任务状态为 `已成功`，任务详情中可见导入表结果与导入行数。
- 当前运行状态显示目标库为 `MySQL`。
- 重启后系统仍可正常登录、查询、下单、核销、入库。
- 关键业务数据与演练前基线一致或符合新增测试数据预期。

### 5.4 验收记录建议

- 记录迁移任务 ID。
- 记录切换时间、重启时间、验收完成时间。
- 记录执行人、验收人、是否通过。

---

## 6. 场景二：失败场景

### 6.1 目标

验证向导在异常条件下能正确阻断或失败留痕，且不会误切换数据库。

### 6.2 推荐演练方式

可任选一种方式制造失败：

- 使用错误的 `MySQL` 密码，验证预检失败。
- 指向一个不可访问的 `MySQL` 主机，验证连通性失败。
- 指向一个已有业务数据且未开启“允许目标库已有业务数据”的目标库，验证风险阻断。

### 6.3 操作步骤

1. 进入 `数据库迁移助手`。
2. 填写有意制造异常的目标库信息。
3. 点击 `执行预检`。
4. 如页面允许继续，则尝试创建任务并执行，观察失败状态。
5. 检查任务详情中的失败原因、预检问题与当前运行状态。

### 6.4 预期结果

- 预检页面出现明确的阻断或警告信息。
- 若存在阻断错误，页面不应鼓励继续创建迁移任务。
- 即使任务执行失败，当前运行状态也不应自动切到异常 `MySQL`。
- 页面能保留失败原因，便于后续排障。

### 6.5 验收重点

- 失败信息是否清晰，运维是否能直接判断下一步处理方向。
- 失败后原系统是否仍保持在原数据库模式。
- 原有业务页面是否仍正常可用。

---

## 7. 场景三：重启场景

### 7.1 目标

验证“写入运行时覆盖配置”与“数据库真正生效”之间存在重启边界，避免误判已经切换完成。

### 7.2 操作步骤

1. 先完成一个成功的迁移任务，但在点击 `切换` 后先不要立即做业务验收。
2. 返回 `数据库迁移助手` 查看当前运行状态与重启提示。
3. 在未重启后端前，观察系统实际数据库行为是否仍保持旧模式。
4. 按运维流程重启后端服务。
5. 重启后再次查看 `数据库迁移助手` 当前模式，并执行一次最小业务动作验证。

### 7.3 预期结果

- 页面应明确提示“写入覆盖配置后通常仍需重启后端服务”。
- 未重启前，不应把“已写入覆盖配置”误判为“已正式完成切换”。
- 重启后，当前运行模式与实际数据库读写行为一致。

### 7.4 验收重点

- 变更单中是否把“写覆盖”和“重启”视为同一次变更闭环。
- 运维值班人员是否清楚未重启前的状态含义。

---

## 8. 场景四：切换恢复与陈旧 SQLite 门禁

### 8.1 目标

验证切换前取消或 MySQL 启动验收失败时可以安全恢复 `SQLite`；同时验证 MySQL 已接收新业务写入后，系统会拒绝切换到陈旧 SQLite。

### 8.2 触发方式

建议在隔离演练环境中分别执行：

- 运行时覆盖已写入、Onebox 尚未切换前主动取消。
- 确定性注入 MySQL 启动/健康检查失败，观察自动恢复。
- 成功切换 MySQL 后新建一张测试订单，再尝试清除覆盖或回到 SQLite。

### 8.3 操作步骤

1. 在隔离环境创建自动迁移任务，覆盖写入后、计划重启前执行取消，并确认 SQLite 内容未变化。
2. 按验收脚本注入 MySQL 启动失败，确认 Onebox 失败重启达到门槛后自动恢复 SQLite，维护态最终解除。
3. 正常迁移并切换到 MySQL，创建一张测试订单作为“切换后新写入”。
4. 返回迁移助手，尝试“回退到 SQLite”或“清除运行时覆盖”。
5. 确认页面禁用危险操作，接口也返回明确阻断；不得通过手工删除运行时文件绕过。
6. 演练真正的灾备路径：从 MySQL 备份恢复到新的 MySQL 实例，或使用经审批的反向迁移工具生成最新 SQLite。

### 8.4 预期结果

- 切换前取消不会污染 SQLite，也不会把系统误切到不完整 MySQL。
- 启动验收失败时，状态机恢复 SQLite 后仍能通过关键业务检查。
- MySQL 产生新写入后，直接回到旧 SQLite 的操作在前端与服务端均被拒绝。
- 最新数据的恢复只来自 MySQL 备份或受控反向迁移，不发生静默丢单。

### 8.5 验收重点

- 自动恢复动作是否可在限定窗口内完成。
- SQLite 一致性快照和 MySQL 备份是否都真实可恢复。
- 门禁是否能阻止把陈旧 SQLite 当作实时数据库。

## 10. 正式上线前放行条件

满足以下条件后，才建议安排正式迁移：

- 四个场景至少完成一轮演练并留痕。
- 成功场景与恢复/陈旧库门禁场景均已验证通过。
- 运维明确知道重启边界，以及切换后不能直接回旧 SQLite。
- 业务验收人已确认关键链路清单。
- SQLite 备份、MySQL 权限、值班窗口均已准备完毕。

---

## 11. 结论

Y-Link 的正式数据库迁移不应再依赖零散的手工步骤。推荐统一通过`数据库迁移向导`完成预检、执行、切换和重启，并通过本文覆盖的四个场景先演练、后上线。切换后恢复以最新 MySQL 数据为准，绝不能用陈旧 SQLite 换取表面上的快速回退。
